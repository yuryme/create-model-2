# Совместная разработка человек–ИИ для автоматизации учётных задач на платформе BaSYS

## Цель проекта

Создать рабочий процесс, в котором задачи автоматизации бизнес-учёта на платформе BaSYS решаются совместно человеком-руководителем и тремя ИИ-ассистентами в строго разграниченных ролях. Платформа BaSYS — отечественное LowCode-решение для бизнес-приложений; конфигурация прикладной системы задаётся набором JSON-файлов метаданных, описывающих справочники, документы, регистры, отчёты, меню и серверные скрипты. Замысел проекта — поручить рутинную генерацию этих метаданных ИИ-ассистентам, оставив за человеком формулировку задач, архитектурный надзор и принятие ключевых решений.

## Архитектура взаимодействия

В проекте работают четыре участника, каждый в отдельной сессии:

**Руководитель (человек)** формулирует бизнес-задачи, удерживает архитектурное и предметное видение, утверждает методики, технические задания и реализации, координирует ассистентов.

**Аналитик (ИИ)** проектирует решение: исходя из формулировки руководителя, предлагает архитектурный подход средствами платформы, после его одобрения пишет детальное техническое задание по утверждённому шаблону. Программный код не пишет.

**Инженер (ИИ)** реализует утверждённое техническое задание: создаёт JSON-файлы метаданных и серверные скрипты на встроенном JavaScript-диалекте платформы, готовит инструкции по импорту на сервер. До правок в исходный код обязательно пишет план реализации, который руководитель также утверждает.

**Ассистент руководителя (ИИ)** помогает координировать ход работы: проверяет методики и задания на соответствие правилам проекта, ведёт ключевые рабочие документы, готовит формулировки для передачи в чаты Аналитика и Инженера. Помимо координации, ассистент развивает саму среду разработки проекта — структуру каталогов и файлов, правила, скиллы, ролевые загрузчики ассистентов — по мере появления новых возможностей платформы Claude Code, на которой работают ИИ-ассистенты. Поддерживает документацию проекта и инструкции для ассистентов в актуальном состоянии: фиксирует принятые решения, обновляет сводку текущего состояния проекта, ведёт ретроспективу по завершённым этапам.

Каждый ИИ-ассистент запускается в собственной сессии с предзагруженной ролью. Это даёт изоляцию контекста: чат Аналитика не «помнит» обсуждение реализации, чат Инженера — обсуждение проектирования. Такая разделённость снижает риск смешения уровней рассуждения и облегчает приёмку.

## Этапы разработки

Работа по любой задаче проходит пять стадий, каждая с собственным артефактом и формальной приёмкой:

1. **Формулировка задачи** (Руководитель). Описание бизнес-задачи своими словами: что нужно автоматизировать, какие сценарии работы, какие ограничения, какие нормативные требования. Это вход для Аналитика.

2. **Методика решения** (Аналитик). Получив формулировку, Аналитик предлагает архитектурное решение — как доступным инструментарием платформы (виды метаобъектов, проведение по регистрам, программируемые команды, процессы) можно решить эту задачу. Цель этой стадии — выбрать архитектурный вариант, наиболее оптимальный для реализации средствами BaSYS: рассмотреть альтернативы, зафиксировать ключевые компромиссы, задать открытые вопросы, на которые нужен ответ руководителя до перехода к детализации. Методика — короткий документ, около двухсот строк, без таблиц колонок и без кода.

3. **Техническое задание** (Аналитик). Пишется после одобрения методики. Детальная спецификация: колонки, типы данных, формулы, поведение при проведении документов, описание серверных скриптов словами, чек-лист приёмки. Шаблон зафиксирован в репозитории, обязательность каждого поля размечена явно.

4. **План реализации** (Инженер). Пишется после одобрения задания. Содержит выбор Инженера по техническим развилкам, оставленным Аналитиком, декомпозицию работы на этапы, оценку объёма и риски.

5. **Реализация** (Инженер). Генерация файлов метаданных и серверных скриптов в каталоге проекта, поэтапная сдача с приёмкой на стенде.

На стадиях со второй по пятую руководитель проводит приёмку через Ассистента: сверяет с предыдущими документами, проверяет на противоречия с правилами проекта. Только после явного одобрения работа переходит к следующей стадии.

## Управление правилами и знаниями

Проект организован вокруг трёх типов документов.

**Архитектурные решения** — короткие записи. Например: «Имена новых объектов и колонок — только латиница в snake-нотации, не более тридцати символов»; «Уникальные идентификаторы видов и типов берутся только из собственного каталога системы, не из чужой выгрузки». Каждое решение принимается после эмпирической находки и фиксирует правило для всех будущих задач.

**Скиллы ассистентов** — пакеты инструкций и тематических справочников, которые подгружаются ассистенту по контексту. Например, скилл по работе с метаданными BaSYS содержит одиннадцатишаговую процедуру создания нового метаобъекта и шесть тематических справочников: команды, отчёты, проведение по регистрам, процессы, меню, импорт из Excel.

**Контекстные файлы** проекта — краткая сводка текущего состояния, живой список открытых вопросов, ретроспектива по завершённым этапам. Поддерживаются ассистентами автоматически в конце каждой смысловой главы работы.

## Что уже сделано

Развёрнута рабочая среда: локальный клон официальной документации BaSYS с картой-индексом, банк структурных образцов из чужой действующей системы, пустая исходная модель проекта, шаблоны технических заданий, методик и планов реализации, скиллы всех трёх ролей.

Проведена серия из четырёх учебных задач возрастающей сложности — от простого справочника до бизнес-процесса с условной маршрутизацией. Все четыре задачи реализованы, импортированы на стенд и приняты. По результатам серии собрана ретроспектива с восемью эмпирическими находками, каждая зафиксирована либо как архитектурное решение, либо как правило в соответствующем скилле, либо как уточнение шаблона задания.

В качестве первого крупного сквозного эксперимента выбран учёт склада со средневзвешенной себестоимостью продаж по нормативу ПБУ 5/01. Конфигурация содержит три справочника (единицы измерения, контрагенты, товары), два документа — закупку и продажу, один накопительный регистр движений товаров со знаком, два отчёта на основе данных регистра (текущие остатки по всем товарам и журнал движений выбранного товара за период) и две программируемые команды на форме документа продажи — «Заполнить себестоимость» и «Провести». Каждая команда выполняется отдельным серверным скриптом. Всего — девять метаобъектов и четыре серверных скрипта.

Содержательная сложность эксперимента сосредоточена в нескольких узлах. Справочник товаров ссылается на единицы измерения и на группу товаров — первый пример ссылочной целостности между несколькими справочниками. Документы закупки и продажи содержат табличные части с расчётной колонкой «сумма строки» через декларативную формулу платформы. Команда «Заполнить себестоимость» при нажатии пользователем строит запрос к накопительному регистру, агрегирует движения по каждому товару с фильтром по дате документа и рассчитывает средневзвешенную, заполняя колонку себестоимости в табличной части продажи. Команда «Провести» перед записью движений в регистр повторно пересчитывает средневзвешенную и сверяет с тем, что уже записано в строках документа: при расхождении проведение отклоняется с явным сообщением пользователю. Это первая для проекта связка из трёх элементов — программируемая команда, прямой серверный запрос к регистру и валидация при проведении документа.

Дополнительная методическая сложность — импорт на сервер: метаобъекты содержат много перекрёстных ссылок между видами, а сервер при импорте обходит файлы алфавитно по папкам видов и не строит граф зависимостей. Поэтому импорт разбит на пять партий с приёмкой на стенде после каждой. Эксперимент проходит финальную приёмку.

## Промежуточные выводы

Подход рабочий. Разделение ролей и приёмка по этапам существенно снижают риск «отчёт-сюрприз», когда расхождение обнаруживается только по факту полной реализации. Дисциплина «методика до задания» уже однажды окупила себя: первая версия методики содержала архитектурное решение, которое было заменено по итогам обсуждения с руководителем, и сделано это было до написания детального задания.

Обратная сторона очевидна: процесс требует активного участия руководителя на каждой стадии. Полностью автономной разработки не получается — да и не предполагалось. Реалистичная цель — снижение трудозатрат руководителя по сравнению с написанием всей конфигурации вручную, при сохранении полного контроля над архитектурой и приёмкой результата.
