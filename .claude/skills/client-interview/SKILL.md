# Скилл `client-interview`

> **Версия скилла:** 0.4 (2026-05-20). Синхронизирован с `playbook-source.md` v2.0.

## Назначение

Точка входа в методику интервью с клиентом. **Скилл не содержит самой методики** — она целиком в `project/docs/interviews/playbook-source.md`. Скилл маршрутизирует к нужным разделам playbook и удерживает жёсткие правила, которые нельзя забыть ни в одной из фаз.

При первом обращении в сессии — обязательно прочитать `project/docs/interviews/playbook-source.md` целиком, дальше работать по памяти раздела с уточнением деталей по запросу.

## Иерархия методики

```
Проект клиента
└── Серия Бесед (1, 2, 3, …)
    └── Беседа = одна встреча, имеет состав:
        ├── Темы беседы (каталог в разделе 4 playbook)
        └── Модули (каталог в разделе 6 playbook)
```

Состав каждой беседы (какие Темы, какие Модули, какая глубина) определяется PM и Аналитиком **на подготовке беседы** и в ходе беседы не меняется (принцип П10).

## Когда подключается

| Фаза | Когда | Что делает скилл |
|---|---|---|
| Подготовка беседы (раздел 5 playbook) | До встречи с клиентом | Поднимает чек-лист подготовки; помогает PM и Аналитику зафиксировать состав беседы (Темы + Модули + глубина); для первой беседы — собрать контекст компании; для последующих — свериться с предыдущим summary. |
| Сама беседа (Темы T1–T6 + Модули, раздел 4 и 6 playbook) | Очно/онлайн с клиентом | Скилл во время беседы не используется (PM и Аналитик ведут диалог по бумажному/экранному playbook, не через Claude). |
| Закрытие беседы (раздел 5 playbook) | В конце беседы | Напоминает обязательные действия закрытия — чек достаточности по составу, договорённость о следующей беседе. |
| Постобработка (раздел 5 playbook) | После беседы | Помогает Аналитику оформить файл `project/docs/interviews/<YYYY-MM-DD>-<client-slug>-conv<N>-summary.md` по шаблону раздела 7 playbook. |
| Обновление методики | По итогам реальных бесед | При правке `playbook-source.md` — синхронизировать этот скилл (см. раздел «Синхронизация» ниже). |

## Маршрутизация по ролям

| Кто | Где работает | Что делает |
|---|---|---|
| PM (пользователь) | Чат PM | Согласует с Ассистентом PM состав каждой беседы (Подготовка); ревьюит summary от Аналитика; передаёт итоговую формулировку задачи Аналитику после серии бесед. |
| Ассистент PM | Чат PM | Помогает PM на Подготовке каждой беседы; владеет этим скиллом — правит при изменениях playbook. |
| Аналитик | Чат `/analyst` | Ведёт методологию на беседе вместе с PM; оформляет файл summary после каждой беседы (Постобработка); из принятой формулировки задачи стартует стандартный двухэтапный цикл (методика → ТЗ). |
| Клиент | Очно/онлайн | Отвечает на вопросы. Только бизнес-язык, без терминов платформы. |

## Жёсткие правила (выжимка из playbook)

Не дубликат методики — короткий «памятный конспект» того, что нельзя нарушать ни в одной фазе любой беседы:

1. **Только бизнес-язык** с клиентом. «Метаобъект», «регистр», «справочник» — наши слова, не клиента.
2. **As-is перед to-be.** Реальный процесс важнее идеального.
3. **Боль важнее желаний.** Платить будут за устранение конкретной боли.
4. **Границы обязательны.** Что НЕ автоматизируем — фиксируется явно.
5. **Не угадывать.** «Обычно» — переспрашиваем «всегда или с исключениями?». «Много» — «штук в день, в неделю, в месяц?».
6. **Один вопрос за раз. Ждать ответа.** Не задавать пачкой, даже если кажется, что вопросы связаны.
7. **Реплики-связки между вопросами — только содержательные.** Короткое повторение факта клиента допустимо; метафоры, образные перифразы, эмоциональные оценки запрещены. Если нечего подтвердить фактом — сразу к следующему вопросу.
8. **Каждую названную боль раскручивать симметрично — до конкретной истории, цифр, последствий.** Тема T2 «Боли» не закрыта, пока хоть одна боль остаётся декларацией.
9. **Состав беседы фиксирован на подготовке.** В ходе беседы при упоминании клиентом области из Модуля, не входящего в состав, **не переключаемся** — фиксируем как кандидата на следующую беседу. На «резюме после Темы» сообщаем клиенту: «эта тема нас вывела на следующие модули — будем сейчас обсуждать» (план не меняется).
10. **Обязательный вопрос Темы или Модуля переформулируется под бизнес клиента, не пропускается.** Пропуск допустим только как осознанное «у клиента нет такой сущности», не «формулировка плохо ложится».
11. **У интервью две цели:** (а) сформулировать задачу, (б) собрать достаточно исходных данных по каждому затронутому бизнес-блоку. Чек достаточности на Закрытии каждой беседы — обязателен.
12. **Объём беседы регулируется составом, не сокращением.** Если состав плотный — уменьшать число Тем/Модулей на подготовке, а не урезать вопросы внутри. Правило-ориентир: 1 модуль = всё ядро; 3 модуля = 3–4 из ядра каждого; 5+ модулей — слишком плотно.
13. **Артефакт каждой беседы = файл** `project/docs/interviews/<YYYY-MM-DD>-<client-slug>-conv<N>-summary.md`, где `<N>` — порядковый номер беседы в серии. Не «сообщение в чате».
14. **После завершения серии бесед** — итоговая формулировка задачи (раздел 7 playbook, пункт 2 последнего summary или сводно по серии) идёт в стандартный двухэтапный цикл Аналитика: методика (`<NN>-design.md`) → ТЗ (`sp-<NNN>-<short-name>.md`).

## Что делает скилл при вызове

`/client-interview` без аргументов:

1. Прочитать `project/docs/interviews/playbook-source.md`, если ещё не прочитан в этой сессии.
2. Показать пользователю короткую карту:
   - Иерархия методики: Серия Бесед → Беседа → (Темы + Модули) → Закрытие → Постобработка.
   - 6 содержательных Тем (T1 Знакомство, T2 Боли, T3 Процесс as-is, T4 Учётные сущности, T5 Критерии успеха, T6 Границы scope).
   - 3 служебные фазы (Подготовка, Закрытие, Постобработка).
   - 6 предметных модулей (M1 продажи, M2 закупки, M3 склад, M4 финансы и управление ДС, M6 расчёты с контрагентами, M5 аналитика для руководителя).
3. Спросить, какая фаза или какая беседа интересна, и углубиться в нужный раздел playbook.

При триггерах model-invocation (например, «готовимся к беседе с клиентом Х») — те же шаги, но с уклоном в фазу, упомянутую в запросе.

Подкоманды (`prepare`, `summary`) пока не реализованы — ждём первого живого интервью, чтобы понять, что реально автоматизировать.

## Что скилл НЕ делает

- **Не ведёт беседу за Аналитика.** Вопросы клиенту задаёт человек, не Claude.
- **Не пишет ТЗ из summary.** Это работа Аналитика в его двухэтапном цикле; скилл `client-interview` отдаёт эстафету скиллу `analyst`.
- **Не хранит содержательную методику.** Только маршрутизирует к `playbook-source.md`.
- **Не отвечает на содержательные вопросы по уже принятому ТЗ.** Для этого есть `basys-metadata` и сам файл ТЗ.

## Синхронизация с playbook-source.md

Источник правды — `playbook-source.md`. Этот скилл — тонкая обёртка. Порядок синхронизации:

1. Содержательные правки методики — всегда **сначала в `playbook-source.md`** (содержательная зона Аналитика), затем в скилле (зона Ассистента PM).
2. При правке playbook обновить здесь:
   - Поле «Версия скилла» в шапке + дата + ссылка на новую версию playbook.
   - Раздел «Жёсткие правила», если в playbook сменился набор принципов или формат артефакта.
   - Раздел «Маршрутизация по ролям», если сменилась граница ответственности.
   - Раздел «Что делает скилл при вызове», если меняется иерархия методики, состав каталогов Тем/Модулей или добавляются подкоманды.
3. История правок скилла — в конце этого файла, по образцу playbook.
