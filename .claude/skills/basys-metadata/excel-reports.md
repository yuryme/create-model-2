# Отчёты Excel (`excel_report`)

**Supporting-файл скилла `basys-metadata`.** Открывать при работе с Excel-отчётами (печатные формы, регламентированная отчётность, отчёты по макету). Основной файл скилла — `SKILL.md`.

**Первоисточник:** `basys-docs/ru/reporting/excelReport.md`.

## Что такое Excel Report

**Отчёт Excel** в BaSYS — метаобъект вида `excel_report`, который собирает отчёт, заполняя заранее подготовленный `.xlsx`-шаблон значениями из JS-источников данных. Шаблон содержит статическую разметку (заголовки, объединённые ячейки, форматирование, обводки, шрифты) и специальные маркеры (`{{...}}`, именованные диапазоны), которые серверный движок (`ClosedXML.Report`) заменяет данными при сборке.

## Когда использовать

Предпочитать Excel-отчёты перед `data_view` **только** когда задача требует одного из:

- **регламентированная отчётность** — фиксированные государственные/отраслевые формы, где каждая ячейка — отдельный расчёт, а компоновка строго определена;
- **печатные формы документов** — счета, накладные, акты, договоры, заявления, которые должны точно соответствовать образцу;
- **тяжело форматированные сводные отчёты** — многоуровневые заголовки, объединённые ячейки, ручные разрывы страниц, корпоративная брендинга, которые не воспроизводятся индикатором `data_view`.

**Для обычных таблиц/дашбордов/графиков/KPI/сводных — `data_view` (см. `data-view-reports.md`).** Сборка `.xlsx` существенно тяжелее (парсинг шаблона, вычисление формул, сериализация), preview в приложении ограничен (один лист, без графиков/сводных/условного форматирования), а итоги через `<<sum>>`-разметку в превью не отображаются.

## Размещение файлов

- У вида `excel_report` флаги `StoreData = false` и `IsReference = false` → запись в `system/dataTypes.json` **не нужна**.
- Settings-файл: `project/metadata/excel_report/{name}/excel_report.{name}.json` — валидируется по `system/schemas/excelReportSettings.schema.json`.
- Верхний уровень — стандартные поля метаобъекта (`Uid`, `Name`, `Title`, `Memo`, `IsActive`, `Version`) плюс две коллекции: `DataSources`, `Filters`.
- **Шаблон** — отдельный бинарный `.xlsx`-файл в той же папке, имя **строго**: `excel_report.{name}.template.xlsx` (именно это имя пайплайн импорта ищет; **не выдумывать** другое и **не вкладывать** содержимое шаблона в JSON).
- **Шаблон не упомянут в JSON.** Связка — по соглашению об имени файла.
- Скрипты источников данных — отдельные `.bjs`-файлы в той же папке: `excel_report.{name}.data_source.{dataSourceName}.bjs`.
- **Нет** `Header`/`DetailTables`/`Commands`/`Forms`/`RecordsSettings` — у Excel-отчёта нет пользовательских данных и нет формы редактирования.

### Работа с шаблоном `.xlsx`

`.xlsx` — бинарный (zip) формат. **AI не должен пытаться сгенерировать, модифицировать или переписать файл шаблона программно** — любая такая запись повредит workbook.

Правила:

- **Создание нового Excel-отчёта:** AI создаёт только `.json` settings и `.bjs` источники. Пользователю нужно сказать, что он сам подготовит `excel_report.{name}.template.xlsx` в Excel (или совместимом редакторе) и положит в папку метаобъекта; напомнить про синтаксис маркеров и именованных диапазонов ниже. **Не** создавать placeholder `.xlsx`.
- **Правка существующего Excel-отчёта:** относиться к существующему `.xlsx` как к чёрному ящику. Можно переименовывать источники данных, фильтры и маркеры в JSON/`.bjs` — но **только** одновременно проинструктировав пользователя обновить соответствующие маркеры/именованные диапазоны в шаблоне. Имена в JSON-стороне и в шаблоне должны синхронизироваться. **Никогда не редактировать `.xlsx` напрямую.**
- То же относится к `.xlsb`, `.xls` и другим бинарным Excel-форматам — они вне области; шаблон **обязан** быть `.xlsx`.

## Источники данных

Каждая запись `DataSources` объявляет именованное выражение, чей результат становится доступным в шаблоне (и последующим источникам) под этим именем.

| Поле | Назначение |
|---|---|
| `Uid` | Свежий UUID v4. |
| `Name` | Идентификатор (snake_case латиницей). Становится ключом в `_data` и именем маркера в шаблоне. |
| `Expression` | Имя файла `.bjs`-скрипта (например, `excel_report.sales_report.data_source.rows.bjs`). |
| `Memo` | Короткое описание (по-русски). |

### Ключевые правила

- Источники вычисляются **строго в порядке объявления**. Поздние источники могут использовать ранние результаты через `_data.<earlierName>`. **Порядок важен** — сначала базовые запросы, потом производные агрегаты.
- `Expression` — **имя файла** `.bjs`-скрипта (не тело). Создавать **обе стороны**: запись в `DataSources` и сам `.bjs`-файл.
- Скрипт **обязан `return`-ить** результат.
- Внутри скрипта доступны три неявные переменные:
  - **`_filters`** — массив активных значений фильтров. Передавать в QueryBuilder через `.withFilters(_filters)`.
  - **`_data`** — словарь результатов **ранних** источников по их `Name` (например, `_data.rows`).
  - **`_parameters`** — словарь параметров вызова (редко).
- Для БД — **QueryBuilder** (`from('kind.name')...query()`).
- При запросах ссылочных полей — `.getDisplays()`, чтобы получить отображаемые значения как `<column>_display` для маркеров шаблона.
- Ограничивать объём данных (`.top(N)`, фильтры, агрегаты) — `.xlsx`-генерация дорогая.

### Поддерживаемые типы возврата

| Тип | Доступ в шаблоне | Замечания |
|---|---|---|
| Скаляр (string/number/date/bool) | `{{sourceName}}` | |
| Объект/словарь/`Expando` | `{{sourceName.property}}` | Сервер преобразует словарь в типизированный CLR-объект на лету (кэширует по сигнатуре). После преобразования — доступ через точку. |
| Коллекция типизированных объектов | `{{item.Property}}` внутри именованного диапазона | В шаблоне должен быть **именованный диапазон** с именем = `Name` источника. Движок повторяет область диапазона на каждый элемент. |
| `DataTable` | `{{item["ColumnName"]}}` или `{{item[index]}}` | Передаётся как `DataRowCollection`. Тоже требует именованного диапазона с именем источника. |

### Подсчёт итогов

Итоги обычно вычислять в **отдельном источнике**, который потребляет основной через `_data`, а в шаблоне тянуть как обычные маркеры. Агрегатная разметка `ClosedXML.Report` (`<<sum>>`, `<<count>>`, ...) формирует **формулы Excel**, чьи значения вычисляются только при открытии файла в Excel — в превью приложения они пустые. Итоги в отдельном источнике видны в превью и снижают нагрузку на движок.

### Пример

`excel_report/sales_report/excel_report.sales_report.json` (фрагмент):

```json
"DataSources": [
  {
    "Uid": "3f5eb097-ca63-2414-4a5f-5ee0dc4e342e",
    "Name": "rows",
    "Expression": "excel_report.sales_report.data_source.rows.bjs",
    "Memo": "Строки отчёта — выгрузка движений по регистру с фильтрами формы."
  },
  {
    "Uid": "6179d17a-74ca-6a78-60c7-8d37eeb5a49f",
    "Name": "totals",
    "Expression": "excel_report.sales_report.data_source.totals.bjs",
    "Memo": "Итоговые суммы, рассчитанные поверх _data.rows."
  }
]
```

`excel_report.sales_report.data_source.rows.bjs`:

```javascript
var tableResult = await from('records.sales')
  .select(['period', 'contract as contract', 'amount as amount'])
  .getDisplays()
  .orderBy('period desc')
  .withFilters(_filters)
  .top(100)
  .query();
return tableResult;
```

`excel_report.sales_report.data_source.totals.bjs`:

```javascript
var amountTotal = _data.rows.sum('amount');
var result = {
  amount: amountTotal,
};
return result;
```

В шаблоне `rows` — это именованный диапазон с ячейками типа `{{item["contract_display"]}}` / `{{item["amount"]}}`, а итоги в обычных ячейках как `{{totals.amount}}`.

## Фильтры

`Filters` настраивают стандартную панель/боковую полосу фильтров BaSYS, интегрированную с QueryBuilder.

| Поле | Назначение |
|---|---|
| `Uid` | Свежий UUID v4. |
| `Name` | Идентификатор параметра в запросах (snake_case латиницей; кириллица допустима только если фильтр сопоставлен с реальной кириллической колонкой источника). |
| `Title` | Метка в UI. |
| `DataPath` | Опциональный путь к колонке внутри источника (обычно `""`). |
| `DataTypeUid` | UID типа из `system/dataTypes.json`. |
| `NumberDigits` | Знаков после запятой для числовых фильтров (иначе `0`). |
| `DefaultComparisonKind` | Дефолтный оператор: `0` Equal, `1` NotEqual, `2` Greater, `3` GreaterOrEqual, `4` Less, `5` LessOrEqual, `6` Between. |
| `RenderPlace` | `0` Sidebar, `1` Header (над командной панелью). |
| `ControlKindUid` | UID контрола ввода (period picker, reference picker, date, number, ...) — скопировать с рабочего фильтра того же типа. |
| `JoinOperator` | `0` And, `1` Or — как фильтр комбинируется с соседними. |
| `Required` | `true` — отчёт не соберётся, пока не заполнили. |
| `AvailableComparisonKinds` | Опциональный whitelist операторов (пустой массив = все). |

Активные значения фильтров передаются в каждый источник через неявный `_filters` и применяются к QueryBuilder через `.withFilters(_filters)`. QueryBuilder ищет каждый фильтр по `Name` и применяет соответствующую пару колонка/оператор, поэтому `Name` фильтра должен совпадать с ключом колонки из `select` (или `getDisplays`).

## Маркеры шаблона — краткая справка

AI не пишет `.xlsx`-файлы, но инструктирует пользователя по синтаксису маркеров при проектировании/правке шаблона:

- **Скалярное значение:** `{{sourceName}}` (например, `{{period}}`).
- **Поле объекта:** `{{sourceName.property}}` (`{{totals.amount}}`).
- **Коллекция/DataTable:** разместить в workbook **именованный диапазон** с именем = `Name` источника; внутри использовать `{{item.Property}}` (типизированные коллекции) или `{{item["ColumnName"]}}` / `{{item[index]}}` (`DataTable`).
- **Держать именованные диапазоны узкими.** Включать только ячейки с маркерами или стилизацией — `ClosedXML.Report` обрабатывает каждую ячейку диапазона при разворачивании коллекции. Захват целых строк «впрок» резко замедляет сборку.
- **Вычислять итоги в источниках**, не через `<<sum>>`-разметку, когда итоги должны быть видны в превью.
- Полная разметка ClosedXML.Report (вложенные диапазоны, группировка, сортировка, условные блоки): https://closedxml.io/ClosedXML.Report/docs/en/Markup.html

## Сборка отчёта — чек-лист

1. Подтвердить, что нужен именно `excel_report` (vs `data_view`). Если задача — обычная таблица/график/дашборд, предложить сначала `data_view`.
2. Создать папку `project/metadata/excel_report/{name}/`.
3. Создать `excel_report.{name}.json`, соответствующий `excelReportSettings.schema.json`, со свежим `Uid`, выбранным `Name`/`Title`/`Memo`, `IsActive = true`, `Version = 1`, заполненными `DataSources`/`Filters`.
4. Создать по одному `.bjs`-файлу на каждый источник, возвращающему значение правильного типа (скаляр/объект/коллекция/`DataTable`).
5. **Сказать пользователю** подготовить `excel_report.{name}.template.xlsx` самостоятельно и положить рядом с JSON — описать, какие маркеры и именованные диапазоны должны быть в шаблоне (исходя из имён `DataSources` и колонок, которые каждый источник возвращает).
6. После загрузки шаблона через импорт система сама ставит `HasTemplate = true` — AI этот флаг **не выставляет**.

## Гигиена

- Свежий `Uid` (UUID v4) для метаобъекта и каждого источника/фильтра.
- `Name` для новых объектов/колонок/фильтров — латиница snake_case (существующие кириллические в `reference/` не переименовывать).
- `Memo` заполнен на метаобъекте и на каждом источнике/фильтре (по-русски).
- `IsActive = true`, если пользователь не попросил скрыть.
- Запись в `system/dataTypes.json` **не добавлять** — `excel_report` не reference.
- Примеры — в `reference/metadata/excel_report/`.
