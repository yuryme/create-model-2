# Команды на формах метаобъектов

**Supporting-файл скилла `basys-metadata`.** Открывать только при работе с командами форм. Основной файл скилла — `SKILL.md`.

**Первоисточник:** `basys-docs/ru/commands/` (в т.ч. `programmableCommands.md`).

## Что такое команда

**Команда** — действие, вызываемое нажатием кнопки или пункта меню на форме метаобъекта. Команды описываются в коллекции `Commands` метаобъекта и привязываются либо к шапке (`Header.Uid`), либо к одной из табличных частей (`DetailTables[i].Uid`) через поле `TableUid`.

## Размещение файлов

- **Тело каждой команды хранится в отдельном `.bjs`-файле** в той же папке, что и JSON метаобъекта.
- Шаблон имени: `{kind.Name}.{object.Name}.command.{command.Name}.bjs`
  - Пример: `project/metadata/operation/task/operation.task.command.send_message.bjs`.
- В JSON в поле `Expression` записи `Commands` указывается **только имя файла** (без пути). Тело — в `.bjs`-файле.
- При добавлении/правке команды AI должен обновить **оба места**: запись в `Commands` JSON-а **и** соответствующий `.bjs`.

## Виды команд

Поле `Kind` записи `Commands` использует `MetaObjectCommandKinds`:

| Значение | Имя | Назначение |
|---|---|---|
| `0` | `Custom` | Программируемая команда — произвольный JS-сценарий в `.bjs`. |
| `1` | `Fill` | Упрощённая команда заполнения — заполняет табличную часть из одного выражения-источника. |
| `2` | `PickUp` | Упрощённая команда подбора — открывает диалог подбора в табличную часть из источника. |

### По умолчанию — программируемая (`Kind = 0`)

**Дефолт — программируемая команда**, даже для сценариев подбора и заполнения. Программируемая даёт полный контроль: подготовка данных, индикатор ожидания, флаг `isModified`, вызов workflows, обработка ошибок и т.д.

Упрощённые `Fill` или `PickUp` использовать **только если**:
- В метаобъекте уже есть команды этого упрощённого вида, и мы расширяем его в том же стиле; или
- Пользователь явно попросил упрощённый вариант.

В программируемой команде подбора/заполнения в теле `.bjs`:
- **Подбор:** построить `DataTable`-источник и вызвать `openPickUp(source, '<detailTableName>')`.
- **Заполнение:** построить источник, затем `$t.<detailTableName>.clear().load(source)`; при необходимости пометить форму как «изменённую» — `setIsModified(true)`.

## Структура записи `Commands`

```json
{
  "Uid": "<свежий UUID v4>",
  "TableUid": "<Uid владельца: Header.Uid или DetailTables[i].Uid>",
  "Kind": 0,
  "Title": "<метка на кнопке, обычно по-русски>",
  "Name": "<технический id, snake_case латиницей, например send_message>",
  "Expression": "<имя .bjs файла, например operation.task.command.send_message.bjs>",
  "Memo": "<короткое описание по-русски>",
  "IsActive": true,
  "Parameters": []
}
```

### Особенности по полям

- **`Uid`** — свежий UUID v4.
- **`TableUid`** — `Uid` владельца команды:
  - Header-команда → `TableUid = Header.Uid`;
  - Команда на табличной части → `TableUid = DetailTables[i].Uid` соответствующей части.
- **`Kind`** — обычно `0`. См. выше.
- **`Name`** — латиница snake_case (`send_message`, `pick_up_employees`, `load_from_file`). Уникален в пределах одного `TableUid` (то есть на одной шапке или одной табличной части не должно быть двух команд с одинаковым `Name`).
- **`Expression`** — только имя `.bjs`-файла для `Kind = 0`; пустая строка `""` для упрощённых `Fill`/`PickUp` (у них логика в `Parameters`).
- **`Memo`** — короткое русское описание.
- **`Parameters`** — пусто `[]` для `Kind = 0`. Для упрощённых:
  - `Kind = 2` (PickUp): один параметр `{ "Name": "data_source", "Value": "<await-выражение, возвращающее DataTable>", "DbType": 16 }`.
  - `Kind = 1` (Fill): такой же `data_source` плюс `{ "Name": "clear", "Value": "true" | "false", "DbType": 16 }`.
  - `DbType = 16` соответствует `String` в `DbType` enum.

## Контекст выполнения программируемой команды (`Kind = 0`)

Программируемая команда исполняется **на клиенте**. В теле `.bjs` доступны:

| Имя | Описание |
|---|---|
| `$h` | Шапка объекта данных; поля через `$h.<columnName>`. |
| `$t` | Табличные части объекта: `$t.<tableName>` (как `DataTable`). |
| `$r` | Текущая строка — **только** в командах, привязанных к табличной части. |

Кроме всех функций BaSYS.FX (включая QueryBuilder `from(...)`), доступны функции управления формой:

| Функция | Возвращает | Описание |
|---|---|---|
| `close()` | void | Закрыть форму и вернуться в список. |
| `getIsModified()` | boolean | Текущее значение флага `isModified`. |
| `getIsWaiting()` | boolean | Текущее значение `isWaiting`. |
| `openDialog(config)` | void | Открыть модальную форму другого метаобъекта. |
| `openPickUp(source, tableName, …)` | void | Открыть диалог подбора в табличную часть. |
| `recalculate()` | Promise | Пересчитать формулы текущего объекта. |
| `refresh(tableViewName)` | void | Обновить TableView-контрол по имени. |
| `runWorkflow(name, step, params, …)` | Promise | Запустить серверный workflow и получить данные именованного шага. |
| `save()` | Promise | Сохранить текущий объект. |
| `setIsModified(value)` | void | Установить флаг `isModified`. |
| `setIsWaiting(value)` | void | Показать/скрыть индикатор ожидания. |

Подробности и сигнатуры — `basys-docs/ru/commands/programmableCommands.md`.

### Особенности

- `openPickUp` доступна **только** в командах, привязанных к табличной части.
- `openDialog` доступна в header-команде автоформы и в командах форм конструктора.
- Долгие операции (запросы, `runWorkflow`, загрузка файлов) **оборачивать** в `setIsWaiting(true)` / `setIsWaiting(false)`.
- Для работы с БД **предпочитать QueryBuilder** (`from('kind.name')...query()`) перед обычным JS.

## Добавление новой команды — пошаговая процедура

1. **Определить владельца** — шапка или конкретная табличная часть. Это задаёт `TableUid` и доступные возможности (`$r`, `openPickUp`).
2. **Сгенерировать свежий `Uid`** (UUID v4) для записи в `Commands`.
3. **Подобрать `Name`** в `snake_case` латиницей (`send_message`, `pick_up_employees`, `load_from_file`).
4. **Собрать имя файла** `{kind.Name}.{object.Name}.command.{command.Name}.bjs` и создать файл рядом с JSON метаобъекта.
5. **Добавить запись в `Commands`** с `Uid`, `TableUid`, `Kind = 0`, `Title`, `Name`, `Expression = "<имя файла>"`, `Memo`, `IsActive = true`, `Parameters = []`.
6. **Написать тело `.bjs`-файла** — используя `$h`, `$t`, `$r`, функции BaSYS.FX и form-control функции выше.
7. **Заполнить `Memo`** — одно предложение по-русски, что делает команда.

## Гигиена

- Имя `.bjs`-файла должно **точно совпадать** со значением `Expression` в JSON.
- `Name` команды уникален в пределах своего `TableUid`.
- Комментарии в `.bjs` — на языке окружающих файлов (обычно русский).
- **Никаких сторонних npm-зависимостей.**

## Эмпирические находки runtime (`experiment-large-01`, 2026-05-19)

Раздел собран по результатам отладки команды `operation/sale.fill_cost`. Поведение runtime BaSYS в нескольких местах расходится с тем, что напрямую следует из `programmableCommands.md` и `dataTable.md`. Это **руководство к действию**, а не описание архитектуры — детали могут отличаться между инсталляциями, перед применением сверять с реальным поведением целевой системы.

### `$t.<tableName>` — это НЕ полноценный DataTable

В контексте программируемой команды (`Kind = 0`) объект `$t.<tableName>` поддерживает только подмножество DataTable-API:

| Доступно | Не доступно (TypeError) |
|---|---|
| `$t.<table>.rows` — массив объектов | `$t.<table>.toArray(...)` |
| `$t.<table>.rows.length` | `$t.<table>.process(fn)` |
| `$t.<table>.rows[i].<column>` (чтение) | `$t.<table>.groupBy(...)` |
| `$t.<table>.clear()` | `$t.<table>.filter(...)`, `.orderBy(...)`, `.addColumn(...)` |
| `$t.<table>.load(dataTable)` | прямой `$t.<table>.addRow(...)` (молчаливо не пишет в форму) |

**Правило.** Если нужна обработка данных табличной части (фильтр, group, agg, distinct, итерация с трансформацией) — собрать настоящий `DataTable` (либо через `createTable(...)`, либо через `from('kind.name.detailTable').query()`) и работать с ним. Запись обратно в форму — только через `$t.<table>.clear() + $t.<table>.load(dataTable)`.

### Чтение состояния формы — из `$t.<table>.rows`, не QueryBuilder

После `await save()` форма (`$t.<table>`) и БД могут расходиться: QueryBuilder к табличной части вида `from('operation.<name>.<detailTable>').where('object_uid = @id').parameter('id', $h.number, 11).query()` возвращает **stale-данные** относительно текущего состояния формы (в нашем кейсе — `quantity` в форме = 3, в результате запроса = 1).

**Правило.** Когда нужны актуальные значения текущей сессии редактирования (что видит пользователь на форме) — читать `$t.<table>.rows[i].<col>` напрямую. QueryBuilder к табличной части использовать только когда явно нужна именно версия в БД (например, для аудит-отчёта).

### Ссылочные колонки в источнике для `load()` — пара `<col>` + `<col>_display`

Когда DataTable-источник содержит ссылочную колонку (например, ссылка на `catalog.product`), для корректной загрузки в табличную часть формы через `clear()+load()` источник **обязан содержать обе колонки**: `<col>` (id) и `<col>_display` (отображаемое значение). Если включить только `<col>` — ссылка в строке формы окажется «пустой» (без названия), даже если id корректен.

**Суффикс зависит от инсталляции:**
- В большинстве случаев — `_display` (текущая инсталляция проекта, эмпирически подтверждено).
- В части реф-корпуса встречается `_title` (вероятно, более старая версия платформы).
- **Перед использованием — проверить:** залогировать `$t.<table>.rows[0]` через `console.log` / `throw` и посмотреть, какие ключи реально приходят для ссылочных колонок.

В `$t.<table>.rows[i]` дисплейное значение ссылочной колонки **присутствует автоматически** — отдельный запрос к справочнику для получения title не нужен, можно копировать `g.<col>_display` напрямую в источник.

### Stored-колонки с `Formula` НЕ пересчитываются после `load()`

Если в табличной части есть колонка с `Formula = "quantity * cost_per_unit"` (Stored с Formula), то при заполнении через `clear() + load(dataTable)` значение этой колонки **остаётся пустым**, даже если в источнике других колонок (`quantity`, `cost_per_unit`) есть. `await recalculate()` после `load()` ситуацию **не исправляет** — Formula табличной части не пересчитывается ни автоматически, ни по принудительной команде пересчёта.

**Правило.** Все Formula-колонки, которые нужны после `load()`, **включать в источник явно** и считать их значения JS-кодом до `addRow(...)`:

```javascript
source.addRow({
  product: g.product,
  product_display: g.product_display || '',
  quantity: g.quantity,
  cost_per_unit: unitCost,
  total_cost: g.quantity * unitCost   // <-- Formula пересчитана вручную
});
```

### `alert()` в нашем runtime не показывает окно

В части реф-корпуса видно использование `alert(message)`, но в нашей целевой инсталляции `alert` либо не определён, либо игнорируется тихо (окно не появляется). Для пользовательских сообщений из команды:

- **Ошибка пользователю** — `throw new Error("текст сообщения")`. Платформа отобразит как ошибку команды.
- **Информационное сообщение** — `openDialog({...})` (см. ниже в основной части файла).
- **Диагностический вывод для разработчика** — `console.log("[mycommand] ...")` в DevTools браузера (F12 → Console).

### Шаблон отладки `.bjs`-команды

Когда команда «молча не отрабатывает» (нет ошибок, но эффект не виден):

```javascript
(async function () {
  var diag = [];
  function log(label, value) {
    var s; try { s = (typeof value === 'string') ? value : JSON.stringify(value); }
    catch (e) { s = '<unstringifiable: ' + e.message + '>'; }
    var line = label + ': ' + s;
    diag.push(line);
    try { console.log('[<commandName>] ' + line); } catch (_) {}
  }

  try {
    log('VERSION', 'v1');           // маркер свежести скрипта (см. ниже)
    log('start, $h.number', $h.number);
    // ... основная логика, перемежать log(...) на ключевых шагах
  } catch (e) {
    log('!!! EXCEPTION', (e && e.message) ? e.message : String(e));
    log('!!! stack', (e && e.stack) ? e.stack : '<no stack>');
    setIsWaiting(false);
    throw new Error('<commandName> diag:\n' + diag.join('\n'));
  }
  setIsWaiting(false);
})();
```

При запуске в DevTools видны построчные `[<commandName>] ...` логи; при ошибке/принудительном `throw` — итоговый diag попадёт в текст исключения и будет виден пользователю и в лог сервера.

### Маркер версии в начале скрипта

Изменения `.bjs` в `project/metadata/` не всегда сразу попадают в редактор команды на стенде — между правкой файла и фактическим выполнением может быть кэш браузера, кэш SPA или вообще ручной шаг копирования через BaSys.Constructor. Чтобы убедиться, что выполняется именно свежая версия:

1. В начало `try` ставить `log('VERSION', 'vN');`, где `N` инкрементируется при каждой правке.
2. Запустить команду на стенде, сверить — в diag/console первой строкой должно быть `VERSION: "vN"` соответствующее последней правке.
3. Если строки `VERSION` нет или версия старая — на стенде закэширована/не обновлена предыдущая версия скрипта. Лечение: переимпорт `operation/<name>/` + Ctrl+Shift+R (hard reload); если не помогает — открыть команду в BaSys.Constructor и скопировать содержимое локального `.bjs` вручную.

### Сводное правило заполнения «зеркальной» табличной части

Если по бизнес-логике нужно заполнить одну табличную часть (`B`) данными, производными от другой (`A`) той же операции — например, по каждой строке `goods` создать строку в `cost`:

1. Читать `A` из формы: `$t.A.rows` (НЕ запросом к БД — будет stale).
2. Собрать источник через `createTable([{name: ...}, ...])`.
3. Для каждой строки `A` сделать `source.addRow({...})`, включая:
   - id ссылочных колонок (`product`),
   - дисплей ссылочных колонок (`product_display`, копируется из `$t.A.rows[i].product_display`),
   - все обычные колонки,
   - **явно вычисленные значения Formula-колонок** (Formula через `load()` не пересчитывается).
4. `$t.B.clear(); $t.B.load(source);`
5. `setIsModified(true);`

Без `await recalculate()` — он не пересчитывает Formula табличной части после `load`.
