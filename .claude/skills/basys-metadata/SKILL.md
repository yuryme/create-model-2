# Генерация метаданных BaSYS — правила работы

## 0. Где первоисточник правды

- **Документация платформы:** `basys-docs/ru/` (локальный клон официального репозитория) + карта `basys-docs-index.md`. При сомнениях по синтаксису/полям/правилам — открывать соответствующую страницу через `Read`, не полагаться на память.
- **⭐ Наш собственный `system/`** (`project/metadata/system/`) — **первоисточник UID видов, типов и JSON-схем для целевой инсталляции**, в которую мы импортируем результат. Состав:
  - `system/dataTypes.json` — список типов данных (UID-ы для использования в `DataSettings.DataTypeUid`).
  - `system/kinds/kind.<name>.json` — определения видов метаданных с их UID-ами (для `MetaObjectKindUid`).
  - `system/schemas/*.schema.json` — JSON-схемы для валидации settings-файлов.
  - **Mostly read-only:** сервер регенерирует этот каталог при импорте. **Исключение:** при создании нового объекта вида с `IsReference = true` дописать запись в `dataTypes.json` (см. шаг 11 ниже).
- **Чужой референсный корпус** (`reference/metadata/` + карта `reference/INDEX.md` и детальные `INDEX-<kind>.md`) — **банк паттернов**, как делается реальная работающая модель. **Не использовать как источник UID-ов** — UID видов и типов в чужой инсталляции **отличаются** от нашей. Брать оттуда только структурные подходы, скрипты, имена колонок, идеи; UID-ы — только из своего `system/`.

## 1. Поток работы

1. Пользователь формулирует задачу.
2. AI ищет аналог в `reference/INDEX-<kind>.md` → читает конкретный JSON → выписывает паттерн.
3. AI генерирует/правит JSON-файлы в `project/metadata/`.
4. Человек смотрит diff в Git.
5. Когда набирается осмысленная партия — человек вручную импортирует обновлённые папки в BaSYS через штатный импорт-экспорт.

**Ключевое отличие от чужих BaSYS-проектов:** мы не правим экспорт «на месте» — мы **порождаем** новые объекты в чистой папке `project/metadata/`. Поэтому правил «не переименовывать существующие кириллические `Name`» у нас нет: всё, что мы создаём — на латинице с самого начала (см. ADR-001 в `project/docs/decisions.md`).

## 2. Типы файлов

- **`*.json`** — декларативные настройки метаобъектов. Должны валидироваться по схемам из `project/metadata/system/schemas/`.
- **`*.bjs`** — обособленные скрипты: тела команд, источники данных для `data_view`, источники записей для проведения по регистрам. Лежат **рядом** с JSON метаобъекта, ссылаются из JSON по имени файла (поле `Expression`).
- **`*.vue`** — программируемые UI-компоненты (используются редко, см. `project-setup-guide.md` про «70% автоформы»).

## 3. Что НЕ редактировать

**В `reference/` — ничего.** Это read-only чужой корпус для подсмотра паттернов.

**В `project/metadata/system/` — почти ничего.** Это копия системных определений целевой инсталляции; сервер регенерирует её при импорте. Конкретно:
- `project/metadata/system/manifest.json` (если будет) — управляется системой при экспорте.
- `project/metadata/system/kinds/`, `project/metadata/system/schemas/` — справочники видов и JSON-схемы валидации. **Никогда не редактировать.**
- `project/metadata/system/dataTypes.json` — каталог типов данных. **Только дописывать** новые записи (см. шаг 11 ниже) при создании reference-kind объектов. Существующие записи **не править и не удалять**.

## 4. JavaScript и BaSYS.FX

Вся логика в выражениях, скриптах команд, источниках записей, обработчиках — **JavaScript**. На сервере исполняется через Jint (синхронный) или ClearScript (async); на клиенте — обычный браузерный JS.

- Для табличных данных, запросов к БД, дат — **предпочитать функции BaSYS.FX** обычному JS, когда есть аналог. Полный обзор: `basys-docs/ru/calculations/`.
- **Не вводить сторонние npm-зависимости** — runtime даёт платформа.
- Незнакомую функцию BaSYS.FX **проверять по документации** перед использованием.

## 5. Имена объектов и колонок

Технический идентификатор — поле `Name`; отображаемое название — `Title`. Это **разные** поля.

### Правила для НОВЫХ объектов, колонок и переменных (ADR-001)

- **`Name`** — только латиница, нижний регистр, `snake_case`, цифры и `_`. Осмысленное (`delivery_address`, не `field1`). Длина `Name` объекта — **≤30 символов**.
- **`Title`** — на любом языке (обычно по-русски), это то, что пользователи видят в UI.
- **JS-переменные/функции/параметры:** `camelCase`; **классы/компоненты:** `PascalCase`; **константы:** `UPPER_SNAKE_CASE`.

### Существующие имена в `reference/`

В чужой модели часть `Name`/папок/файлов на кириллице (`акт_монтаж_ме`, `карточка_договора`). Их **не переименовываем** при чтении паттернов — они идентифицируются системой. Но при **копировании** паттерна в свой `project/metadata/` — даём новое латинское имя.

## 6. Поле `Memo`

У большинства метаобъектов, колонок и вложенных сущностей есть `Memo` — свободный комментарий.

- Каждый новый объект/колонка/таблица — заполнять `Memo` (одно-два предложения, по-русски).
- При редактировании существующего — обновлять `Memo`, если описание устарело или пустое.

## 7. Тип колонки: Stored vs Virtual + поле `Formula`

У каждой колонки (в `Header.Columns` и в `DetailTables[i].Columns`) есть поле `Kind` типа `DataObjectColumnKinds`:

- `0` — `Stored`: колонка хранится в БД.
- `1` — `Virtual`: не хранится, значение определяется каждый раз при показе.

И поле `Formula` — общий механизм **определения значения колонки** (не только арифметика). См. `project/docs/glossary.md`, раздел «Formula». `Formula` может: задавать значение выражением от других полей, подтягивать из связанных объектов (справочники, регистры), получать из внешнего API, делать преобразования (фильтрация, приведение типов, агрегация). Пусто = значение задаёт пользователь или попадает извне.

### Правила для новых колонок

- **По умолчанию — Stored (`Kind = 0`).** Виртуальной (`Kind = 1`) делать только если пользователь явно попросил («виртуальная колонка», «не хранится в БД», «только для отображения»). Сомневаешься — спроси.
- Поле `Formula` **независимо** от `Kind`. Stored-колонка с `Formula` — значение **определяется выражением и сохраняется** в БД. Само наличие `Formula` — **не** повод ставить `Kind = 1`.

> ⚠️ **Расхождение с `basys-docs/ru/metadata/metaObjectTableColumn.md`:** официальная документация описывает `formula` узко («формула для вычисляемых полей»). В реальной системе область применения шире — см. глоссарий проекта.

## 8. Добавление нового метаобъекта — пошаговая процедура

Когда пользователь просит создать новый объект (справочник, регистр, документ и т.п.):

1. **Определить вид метаданных.** Проверить `project/metadata/system/kinds/kind.*.json` — какой это вид (catalog, register, operation, ...). Не очевидно — **спросить пользователя явно**, не угадывать.
2. **Найти папку вида** в `project/metadata/` (создать, если её ещё нет): `project/metadata/catalog/`, `project/metadata/register/`, и т.д.
3. **Создать папку объекта** внутри папки вида, имя — `Name` объекта в `snake_case` латиницей (≤30 символов). **Единственное число** для `Name` и `Title` (`product` / `Товар`, **не** `products` / `Товары`).
4. **Создать settings-файл** внутри: `project/metadata/{kind.Name}/{object.Name}/{kind.Name}.{object.Name}.json` — например, `project/metadata/catalog/city/catalog.city.json`.
5. **Выбрать JSON-схему** по флагу `StoreData` вида:
   - `StoreData = true` → `system/schemas/metaObjectStorableSettings.schema.json` (в `$schema` — относительный путь).
   - `StoreData = false` → подходящая схема из `system/schemas/` (если есть).
6. **Установить `MetaObjectKindUid`** — `Uid` выбранного вида (из его `kind.*.json`).
7. **Скопировать стандартные колонки.** Если у вида есть `StandardColumns` — продублировать каждую в `Header.Columns` нового объекта:
   - `StandardColumnUid` = `Uid` стандартной колонки;
   - `IsStandard = true`;
   - `Name`, `Title`, `DataSettings`, `RenderSettings` — копируются из стандартной;
   - `Uid` самой колонки — **свежий UUID v4** (не переиспользовать `Uid` стандартной).
8. **Подобрать `DataTypeUid` для пользовательских колонок** из `project/metadata/system/dataTypes.json` (искать по `Title` или `TypeName`). **Никогда не выдумывать UID.** UID-ы из чужой выгрузки (`reference/`) НЕ использовать — UID одного и того же типа в разных инсталляциях отличаются.
9. **Сгенерировать свежие UUID v4** (lowercase, с дефисами) для нового объекта и каждой новой колонки/вложенной сущности. Каждый `Uid` в файле — уникальный в пределах проекта.
10. **Заполнить `Memo`** на объекте и на каждой новой колонке.
11. **Регистрация типа в `project/metadata/system/dataTypes.json`** — **только если** у вида установлен флаг `IsReference = true` (например, `catalog`, `enum`, `operation`). Для остальных видов (например, `data_view`, `workflow`, `menu`, `excel_report`) этот шаг пропускается. Дописать новую запись в массив `dataTypes.json` со следующими полями:
    - `uid` — то же значение, что и `Uid` нового объекта (НЕ генерировать отдельный UID).
    - `kind` — `Name` вида (`"catalog"`, `"enum"`, `"operation"` и т.д.).
    - `name` — `Name` нового объекта.
    - `title` — `"{Kind.Title}.{Object.Title}"` (например, `"Справочник.Город"`, `"Перечисление.Тип дня"`).
    - `isPrimitive` — `false`.
    - `dbType` — взять из любой существующей записи в `dataTypes.json` с тем же `kind` (все объекты одного вида делят один `dbType`; например, catalogs обычно имеют `11`, enums — `16`). Если в `dataTypes.json` ещё нет ни одной записи этого вида — взять `dbType` из `DataTypeUid` стандартной primary-key-колонки этого вида (`PrimaryKey = true`, обычно `id`).
    - `objectKindUid` — `Uid` вида (то же, что `MetaObjectKindUid` нового объекта).
    - `typeName` — `null`.

    **Зачем:** без этой записи на новый тип нельзя сослаться в `DataTypeUid` других объектов в той же сессии редактирования. При импорте в BaSYS сервер перезапишет этот файл, так что локальная запись будет заменена авторитетной версией с сервера. **Никаких других правок** — не модифицировать и не удалять существующие записи.

После создания файла мысленно проверить его по выбранной схеме перед завершением.

## 9. Чек-лист перед сохранением JSON

1. ✅ `Name` объекта и всех колонок/таблиц — латиница snake_case, ≤30 символов у объекта.
2. ✅ `Title` и `Memo` — заполнены (по-русски, в пределах лимитов: 100 и 300 символов соответственно).
3. ✅ Все `Uid` — свежие UUID v4 (объект, его колонки, табличные части, их колонки, команды, источники).
4. ✅ `MetaObjectKindUid`, `DataTypeUid`, `StandardColumnUid`, прочие платформенные UID — взяты из **`project/metadata/system/`** (целевая инсталляция). **Не выдуманы и не скопированы из `reference/`** (там UID-ы другой инсталляции).
5. ✅ Имя `Header` — `"header"` (соглашение системы).
6. ✅ `Kind` колонок — `0` (Stored), если пользователь явно не попросил Virtual.
7. ✅ `IsStandard = true` у скопированных стандартных колонок.
8. ✅ `$schema` указывает на актуальную схему (относительный путь).
9. ✅ Файл сохранён как **UTF-8 без BOM, LF**.
10. ✅ JSON синтаксически валиден.

## 10. Специальные темы — supporting-файлы

Загружай эти файлы через `Read` только когда тема релевантна — они не нужны в каждой сессии.

- **`commands.md`** — команды на формах: программируемые / Fill / PickUp, файлы `.bjs`, контекст `$h`/`$t`/`$r`, form-control функции. Открывать при «добавь кнопку», «настрой команду подбора», «добавь действие на форму», или при редактировании `*.command.*.bjs`.
- **`data-view-reports.md`** — отчёты на `data_view` (Панели данных): графики, таблицы, KPI, гейджи, сводные. Открывать при запросе про обычный отчёт/дашборд/визуализацию или при редактировании в `data_view/`.
- **`excel-reports.md`** — Excel-отчёты (`excel_report`): печатные формы, регламентированная отчётность, отчёты по `.xlsx`-макету. Открывать при «печатная форма», «регламентированный отчёт по макету», «счёт/накладная/акт», или при редактировании в `excel_report/`. **Не путать с `data_view`** — для обычных таблиц/графиков/KPI использовать `data-view-reports.md`.
- **`records-creation.md`** — проведение по регистрам: `RecordsSettings`, `RecordsSources`, источники записей в `.bjs`, направления Plus/Minus. Открывать при «настрой проведение», «добавь записи в регистр», «создай источник записей», или при редактировании `*.records_source.*.bjs`.
- **`workflows.md`** — процессы (`workflow`): серверные pipeline из шагов (`java_script`, `if`, `iterator`, `read_file`, `excel_mapping`, `data_object_loader`, `http_connector`, `smtp_send`, ...). Открывать при «создай процесс», «настрой импорт из Excel», «добавь шаг workflow», или при редактировании в `workflow/`.
- **`menu.md`** — меню (`menu`): навигационное дерево боковой панели, иерархия группа → колонки → подгруппы → ссылки, ручной vs авто-режим. Открывать при «добавь меню», «настрой навигацию», «авто-заполнение меню справочниками», или при редактировании в `menu/`.

### Готовые рецепты (отдельные скиллы)

- **`/excel-import-to-detail`** — рецепт «Excel → табличная часть операции»: связка workflow (find_file + read_file + excel_mapping) + программируемая команда на табличной части. Триггерится при «загрузи из файла», «импорт Excel в табличную часть», «добавь кнопку "Заполнить из файла"». Использовать когда задача укладывается в этот шаблон; для нетипичных вариантов — комбинировать `workflows.md` + `commands.md` вручную.

## 11. Общение и комментарии

- С пользователем — на языке пользователя (обычно русский).
- Комментарии в коде (`.bjs`, `.vue`) — на языке, уже принятом в окружающих файлах (обычно русский).
- Тексты в `Title`/`Memo` — по-русски.
