# Проведение по регистрам (Records Creation)

**Supporting-файл скилла `basys-metadata`.** Открывать при настройке проведения по регистрам. Основной файл скилла — `SKILL.md`.

**Первоисточник:** `basys-docs/ru/metadata/recordsCreation.md`.

## Что это и когда применяется

Метаобъект вида, у которого `CanCreateRecords = true` (как правило — `operation`), может **формировать записи в одном или нескольких регистрах-приёмниках** (вид `records`). Каждый раз при сохранении объекта-источника предыдущие записи, порождённые им, удаляются и формируются новые по правилам из коллекции `RecordsSettings`.

## Предпосылки

- У **вида** метаданных должен быть выставлен флаг `CanCreateRecords = true`. Для `operation` он уже стоит. Проверять в `project/metadata/system/kinds/kind.<name>.json`.
- В `Header.Columns` объекта-источника должна быть стандартная колонка **`create_records`** (`StandardColumnUid = fee422db-18dc-442a-a8dd-01df76c20a98`). Когда этот флаг `false`, старые записи удаляются, новые не создаются — эквивалент «отмены проведения».
- Регистр-приёмник — это `DataObject` вида `records`, в шапке которого есть стандартные служебные колонки: `MetaObjectKind`, `MetaObject`, `Object`, `Row`, `Period`. Их связь с механизмом задаётся **на виде** (`RecordsSettings` блок в `kind.operation.json`: `StorageKindColumnUid`, `StorageMetaObjectColumnUid`, `StorageObjectColumnUid`, `StorageRowColumnUid`, `StoragePeriodColumnUid`). AI это **не** настраивает — это живёт на виде, не на объекте.
- Колонки `MetaObjectKind`, `MetaObject`, `Object`, `Row` заполняются движком автоматически — **не перечислять их** в `Columns` правила. Колонку `Period` **обязательно** задавать выражением (обычно `$h.date`).

## JSON-структура на объекте-источнике

Две top-level коллекции:

- **`RecordsSources`** — список **источников записей** (custom JS-источники, kind 3 — см. «Виды источников» ниже). Каждая запись ссылается на отдельный `.bjs`-скрипт через `Expression` (только имя файла).
- **`RecordsSettings`** — список **правил**. Каждое правило нацелено на один регистр-приёмник (`DestinationMetaObjectUid`) и содержит одну или несколько `Rows`. Каждая `Rows`-запись указывает (через `SourceUid`) на шапку, табличную часть или источник записей и перечисляет колонки регистра-приёмника с выражениями заполнения.

**Обе коллекции должны присутствовать в JSON операции даже если пустые (`[]`).**

### Запись `RecordsSources`

```json
{
  "Uid": "<свежий UUID v4>",
  "Title": "Группировка по проекту",
  "Expression": "operation.<name>.records_source.<sourceName>.bjs"
}
```

- **`Uid`** — свежий UUID v4. На него ссылается `RecordsSettings.Rows[i].SourceUid`.
- **`Title`** — отображаемый ярлык в дизайнере.
- **`Expression`** — **только имя файла** `.bjs`-скрипта (без пути). Тело скрипта — в этом файле.

> Схема `RecordsSourceItem` **не имеет** поля `Name` — источник идентифицируется по `Uid`, ярлычится через `Title`. Для **новых** источников `Title` должен быть «чистым slug-ом» — snake_case латиницей ASCII (`group_by_project`, `tn_to_kg`), потому что эта же строка становится частью имени файла.

### Запись `RecordsSettings`

```json
{
  "DestinationMetaObjectUid": "<Uid регистра-приёмника>",
  "Rows": [
    {
      "Uid": "<свежий UUID v4>",
      "SourceUid": "<Uid источника>",
      "Direction": 0,
      "Condition": "",
      "Columns": [
        { "DestinationColumnUid": "<Uid колонки регистра>", "Expression": "$h.date" },
        { "DestinationColumnUid": "<Uid колонки регистра>", "Expression": "$r.quantity" }
      ]
    }
  ]
}
```

- **`DestinationMetaObjectUid`** — `Uid` регистра-приёмника (брать из соответствующего `records/<name>/records.<name>.json`). Несколько правил могут целиться в один регистр или в разные.
- **`SourceUid`** — `Uid` выбранного источника на **этом же** метаобъекте (см. «Виды источников» ниже).
- **`Direction`** — enum `RegisterRecordDirections`:
  - `0` — `Plus` (Приход);
  - `1` — `Minus` (Расход). При `Minus` движок **автоматически умножает на `-1`** все decimal-поля сформированной записи. **Не повторять** инверсию знака в выражениях.
- **`Condition`** — опциональное JS-выражение, возвращающее boolean. Если `false` — запись для этой строки источника пропускается. Пустая строка = «всегда создавать».
- **`Columns`** — пары `DestinationColumnUid` ↔ `Expression`. Перечислять только те колонки регистра, которые правило заполняет (включая `Period`). **Не** перечислять авто-заполняемые служебные (`MetaObjectKind`, `MetaObject`, `Object`, `Row`).

У каждой `Rows`-записи — свой свежий `Uid`.

## Виды источников

`SourceUid` в `RecordsSettings.Rows` указывает на один из трёх типов источника **этого же метаобъекта**:

### 1. Шапка (Header)

`SourceUid = Header.Uid` объекта-источника. **Одна запись на объект.** В выражениях доступно только `$h.<columnName>`; использование `$r.<columnName>` упадёт — нет «текущей строки».

### 2. Табличная часть (Detail table)

`SourceUid = DetailTables[i].Uid` одной из табличных частей. **Одна запись на строку** этой части. В выражениях доступны `$h.<columnName>` (поле шапки) и `$r.<columnName>` (поле текущей строки).

### 3. Источник записей (Records source)

`SourceUid = RecordsSources[i].Uid`. **Одна запись на строку** `DataTable`-а, возвращённого скриптом источника (см. ниже). В выражениях доступны `$h.<columnName>` и `$r.<columnName>` (текущая строка **возвращённой** таблицы).

Использовать **источник записей**, когда записи нельзя получить прямо из шапки или какой-то одной табличной части — нужна группировка, разворот (unpivot), слияние, синтез.

## Источники записей как `.bjs`-файлы

Тело каждой записи `RecordsSources` — **отдельный `.bjs`-файл** в той же папке, что и JSON метаобъекта. JSON ссылается через `Expression`.

### Шаблон имени файла

`{kind.Name}.{object.Name}.records_source.{sourceName}.bjs`

Пример: для операции `shipment` с источником `tn_to_kg`:
- В JSON (`Expression`): `"operation.shipment.records_source.tn_to_kg.bjs"`
- Файл: `project/metadata/operation/shipment/operation.shipment.records_source.tn_to_kg.bjs`

Имя файла должно **точно совпадать** с `Expression`. При добавлении/правке — обновлять **обе стороны**.

### Контракт скрипта

Скрипт работает **на сервере** (движок ClearScript) и **обязан `return`-ить `DataTable`**. Движок итерирует эту таблицу и создаёт по одной записи регистра на строку, заполняя её через выражения правила и применяя `Direction`/`Condition`/`Columns`.

Доступные неявные имена:

| Имя | Описание |
|---|---|
| `$h` | Шапка объекта-источника; поля через `$h.<columnName>`. |
| `$t` | Табличные части объекта-источника как `DataTable`; через `$t.<tableName>`. |

> Табличные части — через `$t.`, не через `$h.`. Префикс `$h.` зарезервирован для полей шапки.

Возвращаемый `DataTable` поддерживает цепочечные методы BaSYS.FX: `.select(columns)`, `.addColumn(columnDef)`, `.process(fn)`, `.groupBy(keys, aggregates)` и другие — см. `basys-docs/ru/calculations/dataTable.md`.

### Ограничения текущей версии

- **Произвольные запросы к БД** внутри источника записей **не поддерживаются**. Строить результат **только** из `$h` и `$t`. Нужны предвычисленные данные — готовить их серверным триггером/процессом и заранее складывать в табличную часть.
- Скрипт исполняется на сервере → браузерные API (`alert`, и т.п.) не работают.
- Если скрипт вернул не `DataTable` — движок пишет ошибку и пропускает это правило, не валя остальные.

### Примеры скриптов

Группировка табличной части по ключевым колонкам с суммированием:

```javascript
var source = $t.goods.groupBy(['project', 'mark'], ['total_weight', 'amount']);
return source;
```

Производная колонка и инверсия знака для расходного документа:

```javascript
var source = $t.goods
  .addColumn({ name: 'kg', dataType: 'number' })
  .process(r => {
    r.qty_pcs = r.qty_pcs * -1;
    r.kg = r.total_weight * -1000;
  });
return source;
```

Fallback на случай пустого входа:

```javascript
var t = $t.table_1;
if (t.rows.length > 0) {
  return t.groupBy(['code_km'], ['qty_tn', 'amount_rub']);
}
return createTable([{ name: 'product' }]);
```

## Выражения в `RecordsSettings.Columns`

Каждое `Columns[i].Expression` заполняет одну колонку регистра-приёмника. Движок различает три формы:

- **Поле шапки** — `$h.<columnName>`. Берётся как есть.
- **Поле строки** — `$r.<columnName>`. Берётся из текущей строки выбранного источника (табличной части или результата источника записей). **Не работает** когда источник — шапка.
- **Произвольное выражение** — любое JS-выражение. Вычисляется Jint-ом; `$h.<>` и `$r.<>` допустимы внутри. Результат автоматически приводится к типу целевой колонки.

### Примеры выражений

- `$h.date` — дата из шапки (типичный `Period`);
- `$r.quantity` — количество из текущей строки;
- `$r.quantity * $r.price` — расчётная сумма;
- `$h.warehouse` — поле шапки, применяемое к каждой строке документа;
- `"2"` — жёстко зашитая строковая константа.

`Condition` следует тем же правилам и должна возвращать boolean (`$r.total_weight_kg > 0`, `$h.status > 2 && $h.workshop > 0`, или `false` чтобы временно отключить правило). Пустая строка = «всегда создавать».

## Добавление нового правила в `RecordsSettings`

1. **Подобрать регистр-приёмник** и прочитать его JSON, чтобы взять `DestinationMetaObjectUid` и `Uid` колонок-приёмников. Регистр обязан быть видом `records` со стандартными служебными колонками.
2. **Выбрать источник** для каждой `Rows`-записи:
   - Шапка → `SourceUid = Header.Uid`. Использовать только `$h.*`.
   - Табличная часть → `SourceUid = DetailTables[i].Uid`. Использовать `$h.*` и `$r.*`.
   - Источник записей → `SourceUid = RecordsSources[i].Uid`. Использовать `$h.*` и `$r.*` (текущая строка результата скрипта).
3. **Выбрать `Direction`** — `0` для Приход, `1` для Расход. При `1` **не инвертировать** знак decimal-полей вручную — движок сам.
4. **Написать `Columns`** — по одной записи на каждую заполняемую колонку. Всегда включать `Period` (обычно `$h.date`). Пропускать служебные колонки.
5. **При необходимости — `Condition`** для фильтрации.
6. **Свежие `Uid`** для каждой новой `Rows`-записи.

Если один и тот же объект пишет в несколько регистров — несколько записей `RecordsSettings`, по одной на `DestinationMetaObjectUid`.

## Добавление нового источника записей

1. **Свежий `Uid`** для новой записи `RecordsSources`.
2. **`Title`** — для новых источников использовать чистый snake_case латиницей (`group_by_project`), потому что эта же строка становится частью имени файла.
3. **Имя файла** `{kind.Name}.{object.Name}.records_source.{Title}.bjs`. Создать файл в той же папке, что и JSON метаобъекта.
4. **Запись в `RecordsSources`** с `Uid`, `Title`, `Expression = "<имя файла>"`.
5. **Тело `.bjs`** — `$h`, `$t`, `DataTable`-хелперы BaSYS.FX; скрипт **обязан `return`-ить `DataTable`**.
6. **Привязать источник к правилу** — добавить (или править) запись в `RecordsSettings`, где `Rows[i].SourceUid` = `Uid` нового источника. Заполнить `Direction`, опционально `Condition`, и `Columns`.

## Гигиена

- Имя `.bjs`-файла источника точно совпадает с `Expression` в JSON.
- Существующие имена источников (в `reference/` они часто на кириллице, с пробелами/пунктуацией) **не переименовывать** — они ссылаются по `Uid`, но переименование сломает связку файл↔JSON до следующего экспорта.
- Комментарии в `.bjs` — на языке окружающих файлов (обычно русский).
- Предпочитать `DataTable`-хелперы (`groupBy`, `process`, `addColumn`, `select`, ...) обычным JS-циклам.
- **Никаких сторонних npm-зависимостей.**
