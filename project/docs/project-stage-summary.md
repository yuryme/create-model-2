# Резюме Этапа Работ

Выполнены две связанные работы: создание базовой учетной модели и реализация учета пакетов минут распознавания. Обе работы важны не только как набор metadata-изменений, но и как проверка способности AI-ассистента переходить от бизнес-постановки к структуре прикладной модели: определять необходимые объекты, поля, связи, операции, регистры и алгоритмы обработки данных.

## 1. Базовая Учетная Модель

### Цель

Целью первой работы было создание учетной модели, пригодной для дальнейшего развития конфигурации BaSYS. Задача была поставлена на уровне бизнес-потребности: сформировать базовый контур учетной системы. На основании этой постановки AI-ассистент самостоятельно определил перечень необходимых metadata-объектов, их назначение, состав полей и базовые связи между ними.

Это был важный результат: работа не сводилась к механическому созданию заранее заданного списка JSON-файлов. Сначала была выполнена декомпозиция предметной области на справочники, операции и регистры, после чего уже была реализована metadata-структура.

### Содержание Работ

На основании поставленной задачи был определен состав базовой учетной модели: справочники для нормативно-справочной информации, операции для фиксации хозяйственных событий и регистры для накопления учетных движений. Для каждого объекта был определен набор полей, типы данных и связи с другими объектами.

Были созданы справочники:

- `bank` — банк;
- `bank_account` — расчетный счет;
- `cash_flow_item` — статья движения денежных средств;
- `company` — организация;
- `contract` — договор;
- `counterparty` — контрагент;
- `employee` — сотрудник;
- `product` — номенклатура;
- `product_group` — группа номенклатуры;
- `unit` — единица измерения;
- `warehouse` — склад.

Были созданы операции:

- `goods_receipt` — поступление товаров;
- `goods_sale` — реализация товаров;
- `service_receipt` — поступление услуг;
- `service_sale` — реализация услуг;
- `money_receipt` — поступление денег;
- `money_payment` — списание денег.

Были созданы регистры:

- `stock_records` — складские движения;
- `settlement_records` — взаиморасчеты;
- `money_records` — денежные движения.


### Выявленные Ошибки

В ходе работы была выявлена ошибка именования metadata-поля, связанная с SQL reserved words. Один из технических идентификаторов был несовместим с SQL-ограничениями. Ошибка была диагностирована как проблема имени колонки, после чего было принято решение переименовать поле. Этот случай стал важным правилом для дальнейшей генерации metadata: новые `Name` объектов и колонок должны быть на латинице, в `snake_case`, и не должны совпадать с SQL reserved words.

Вторая значимая ошибка относилась к структуре табличных частей операций. В созданных detail tables отсутствовали обязательные системные колонки:

- `id`;
- `object_uid`;
- `row_number`.

Стенд BaSYS при чтении и сохранении табличных частей строит SQL-запросы с использованием `object_uid` и `row_number`. При отсутствии этих колонок возникала ошибка вида:

```text
column ... object_uid does not exist
```

Сравнение с reference metadata показало, что каждая табличная часть операции должна начинаться с этих трех колонок в фиксированном порядке.

### Процесс Отладки

Ошибка с SQL reserved word была выявлена при проверке metadata и анализе причины некорректного поведения создаваемого объекта. После диагностики стало ясно, что проблема не в типе данных или связи, а в техническом имени колонки. Поле было переименовано, а правило о запрете SQL reserved words было внесено в проектные patterns.

Ошибка с табличными частями была выявлена позже, при проверке операции из второй задачи, но затрагивала и базовые операции. Для диагностики был использован SQL-текст ошибки стенда, после чего локальные JSON-файлы были сопоставлены с reference metadata. В reference-операциях было подтверждено, что `id`, `object_uid`, `row_number` являются обязательным началом каждой табличной части операции.

После этого был выполнен поиск по всем операциям проекта. Дефект был найден и исправлен в табличных частях:

- `goods_receipt.items`;
- `goods_sale.items`;
- `service_receipt.items`;
- `service_sale.items`;
- `recognition_usage.items`;
- `recognition_usage.write_offs`.

### Результат

Создан базовый контур учетной модели BaSYS, включающий справочники, операции и регистры, пригодные для дальнейшего развития конфигурации. Важным итогом стала не только реализация metadata, но и подтверждение, что AI-ассистент способен по общей постановке определить состав объектов, их поля и связи.

Время генерации файлов объектов метаданных - 12 минут.

По итогам проверки были устранены ошибки именования и структуры табличных частей. В проектных правилах закреплены требования к техническим именам и обязательным колонкам detail tables.

## 2. Учет Пакетов Минут Распознавания

### Цель

Вторая работа началась не с запроса на создание конкретных metadata-объектов. Пользователь сформулировал бизнес-проблему: как корректно учитывать оплаченные минуты распознавания, фактический расход и выставление актов/счетов так, чтобы сумма к оплате соответствовала стоимости фактически использованных минут.

Пользователь не формулировал заранее модель через операции, регистры или FIFO-алгоритм. На основании описанной проблемы AI-ассистент предложил методику решения: учитывать покупки как пакеты минут, а фактический расход списывать по пакетам методом FIFO. Эта методика позволила связать оплату, объем купленных минут, фактическое потребление, цену минуты, остатки пакетов и возможный перерасход.

После выбора методики был определен состав metadata-объектов: операция покупки пакета, операция расхода минут, регистр движений минут, workflow загрузки Excel и команды для загрузки и расчета списания.

### Содержание Работ

Была предложена и реализована учетная схема:

- покупка минут фиксируется отдельной операцией `recognition_package`;
- фактическое потребление фиксируется операцией `recognition_usage`;
- все движения минут хранятся в регистре `recognition_minutes`;
- расход списывается по доступным пакетам клиента в хронологическом порядке;
- если доступных минут недостаточно, формируется строка перерасхода;
- результат расчета используется для формирования движений регистра и дальнейшей сверки стоимости.

Были созданы:

- операция `recognition_package` — покупка пакета минут распознавания;
- операция `recognition_usage` — расход минут распознавания;
- регистр `recognition_minutes` — движения минут распознавания;
- workflow `load_rec_usage_excel` — загрузка Excel-файла в табличную часть расхода;
- команда `load_from_file` — вызов workflow из операции расхода;
- команда `calculate_fifo` — расчет FIFO-списания минут по пакетам.

В операции `recognition_usage` были реализованы две табличные части:

- `items` — фактический расход минут по клиентам из Excel;
- `write_offs` — результат распределения расхода по пакетам и перерасходу.

Время генерации файлов объектов метаданных - 29 минут.

Сценарий работы:

- пользователь создает документ расхода минут;
- прикрепляет Excel-файл;
- команда загружает строки Excel в `items`;
- команда FIFO рассчитывает списания по доступным пакетам;
- результат записывается в `write_offs`;
- при сохранении операция формирует движения регистра `recognition_minutes`.

### Выявленные Ошибки

Первая ошибка была в настройке workflow `excel_mapping`. Для колонки клиента был указан reference-тип `Catalog.Контрагент`, тогда как `excel_mapping` поддерживает только primitive-типы. В UI workflow тип данных для строки клиента не отображался. Исправление: Excel стал читаться в промежуточное поле `counterparty_id` с типом `Int`, а reference-значение формировалось на отдельном JS-шаге `result`.

Вторая ошибка касалась загрузки reference-полей через `$t.<table>.load(source)`. Для корректного отображения reference-значений нужно передавать не только ID, но и `_display`-поле. Это было исправлено для загрузки расхода из Excel и для результата FIFO-расчета.

Третья ошибка была связана с отсутствием стандартных колонок `id`, `object_uid`, `row_number` в табличных частях операции `recognition_usage`. Эта ошибка проявлялась при сохранении операции и была устранена добавлением обязательных колонок.

Четвертая ошибка была в FIFO-расчете. Команда исключала текущий документ из регистра только по `object_uid`. На стенде выяснилось, что номера документов разных metaobject могут совпадать. В конкретном случае номер расхода совпал с номером пакета минут. Из-за этого пакет ошибочно исключался из доступного остатка, и система формировала ложный перерасход. Исправление: текущий документ исключается из регистра по паре `meta_object + object_uid`.

Пятая ошибка была инфраструктурной. При прикреплении файла возникала ошибка S3/file storage:

```text
No RegionEndpoint or ServiceURL configured
```

Она не относилась к metadata и была определена как проблема настройки файлового хранилища стенда.

### Процесс Отладки

Сначала была проверена связка операции, команды и workflow. Команда `load_from_file` вызывала workflow `load_rec_usage_excel`, который возвращал результат шага `mapping`. Анализ JSON показал, что проблема не в отсутствии `DataTypeUid`, а в неподдерживаемом reference-типе. После этого был добавлен JS-шаг `result`, который ищет контрагента по `catalog.counterparty.id` и формирует таблицу с `counterparty`, `counterparty_display` и `minutes`.

Затем была разобрана ошибка сохранения операции. SQL из консоли показал обращение к `object_uid` в физических таблицах табличных частей. Сравнение с reference metadata подтвердило необходимость стандартных колонок detail tables.

После этого была проверена команда `calculate_fifo`. В таблицу результата были добавлены display-поля для reference-значений. Затем результат расчета был сопоставлен с регистром `recognition_minutes`. Сравнение показало, что доступных минут достаточно, но один пакет не учитывается из-за совпадения номера с текущим документом расхода. Это позволило локализовать ошибку в фильтре регистра и исправить его.

### Результат

Сценарий учета пакетов минут распознавания работает на стенде:

- Excel-загрузка корректно заполняет фактический расход;
- клиент определяется по ID из Excel;
- reference-поля отображаются корректно благодаря `_display`;
- FIFO-расчет списывает минуты по доступным пакетам;
- ложный перерасход при совпадении номеров разных операций устранен;
- операция сохраняется без SQL-ошибок;
- движения регистра формируются и используются в последующих расчетах.

По итогам работы в `project/docs/patterns/metadata-workflow.md` закреплены правила:

- `excel_mapping` использует только primitive `DataTypeUid`;
- reference-поля при `$t.<table>.load(source)` передаются как `field` + `field_display`;
- табличные части операций начинаются с `id`, `object_uid`, `row_number`;
- регистры фильтруются по `meta_object + object_uid`, а не только по `object_uid`.

Generated BaSYS skills вручную не изменялись.
