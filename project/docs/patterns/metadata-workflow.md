# Metadata Workflow Patterns

Этот документ хранит переиспользуемые выводы из прогонов. Не переносить сюда полные отчёты экспериментов; фиксировать только правила, которые реально ускоряют будущую работу.

## Рабочее Зеркало

- `project/metadata/` — рабочее зеркало текущего стенда BaSYS.
- Перед существенной задачей синхронизировать `project/metadata/` с фактическим стендом.
- После реализации импортировать/проверять изменения на стенде; PM принимает поведение системы, а не JSON-файлы.
- Не делать отдельный promotion metadata из экспериментальной папки, если PM явно не попросил изолированную ветку/worktree.

## Что Сохранять После Run

- Изменения metadata, которые стали текущим рабочим состоянием.
- Краткое ТЗ или import notes, если они нужны для дальнейшей работы.
- Новое правило/ADR/skill-правку, если run выявил устойчивый урок.

## Что Не Сохранять В Активном Контексте

- Длинные review/audit/report файлы экспериментов.
- Временные implementation plans, если они больше не управляют работой.
- Альтернативные metadata-варианты, которые не используются стендом.
- Логи рассуждений агентов.

## Уроки Из Предыдущих Прогонов

- Новые `Name` объектов и колонок — латиница `snake_case`, не SQL reserved words (`group`, `order`, `user`, `select`, `from`, `where`, `table`, `index`, `key`, `value`, `count`, `sum`, `case`, `when`, `default`).
- UID видов, типов, стандартных колонок и схем брать только из `project/metadata/system/`, не из `reference/`.
- `project/metadata/system/dataTypes.json` можно локально дописывать для reference-kind объектов, но сервер BaSYS остаётся авторитетом после импорта/экспорта.
- `manifest.json` — системный экспортный файл; не использовать его как ручной контракт реализации без явной необходимости.
- Если `menu/main` использует `AutoFill = true` для kind, новый объект обычно не нужно добавлять в меню вручную.
- Формы списка/редактирования не создавать по умолчанию. Если в задаче прямо не сказано создать формы, назначить формы или настроить UX, оставлять `ListFormUid`/`ItemFormUid = null` и использовать автоформы BaSYS. Для первой версии или чернового ядра формы не создавать. Если агент считает, что формы нужны, он сначала отдельно спрашивает PM.
- Исключение по формам: если пользователь явно просит форму списка, форму редактирования, кнопку, UX, layout, скрытие/группировку полей или удобный рабочий сценарий пользователя, тогда формы создаются через соответствующие skills.
- Для простого catalog не запускать multi-agent; достаточно quick metadata + self-check.
- Для средних задач с известными паттернами предпочтителен single-agent autopilot: один контекст, внутреннее ревью, без persisted review/audit файлов.
- Multi-agent использовать только там, где независимый reviewer/auditor окупает стоимость.
