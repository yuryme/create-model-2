# Методика решения — Базовая учетная модель для малого бизнеса

## 1. Бизнес-задача

Проект должен стать рабочим инструментом для решения учетных и смежных управленческих задач разных предпринимателей. Чтобы каждую новую задачу не начинать с пустой конфигурации, нужна базовая учетная модель: минимальное ядро справочников, операций и регистров, которое встречается в большинстве бизнесов.

Базовая модель не должна пытаться сразу покрыть все отрасли. Ее задача — дать устойчивую основу: организации, контрагентов, номенклатуру, склады, деньги, базовые покупки, продажи и взаиморасчеты. Поверх этого ядра позже будут добавляться расширяемые блоки: розница, услуги, производство, проекты, CRM, складская логистика, управленческий учет, отраслевые документы и отчеты.

Ключевое требование — простота. Первая версия должна быть понятна предпринимателю и удобна для дальнейшего развития. Поэтому в ней следует избегать сложной бухгалтерской методологии, партионного учета, налогового учета, регламентированной отчетности и отраслевых деталей, пока они не нужны конкретной задаче.

## 2. Архитектурный подход

### 2.1. Предполагаемые метаобъекты

Ниже указан рекомендуемый состав первой версии. Имена технических объектов черновые; точные `Name`, состав колонок и формы должны быть описаны в основном ТЗ после одобрения методики.

| Действие | Вид | Имя (черновик) | Назначение |
|---|---|---|---|
| CREATE | catalog | `company` | Собственные организации / ИП, от имени которых ведется учет. |
| CREATE | catalog | `counterparty` | Покупатели, поставщики и прочие внешние партнеры. |
| CREATE | catalog | `product` | Общая номенклатура: товары, услуги, работы, материалы. |
| CREATE | catalog | `product_group` | Группы номенклатуры. |
| CREATE | catalog | `unit` | Единицы измерения номенклатуры. |
| CREATE | catalog | `warehouse` | Склады и места хранения. |
| CREATE | catalog | `bank` | Банки для платежных реквизитов. |
| CREATE | catalog | `bank_account` | Расчетные счета организаций и, возможно, контрагентов. |
| CREATE | catalog | `contract` | Договоры с контрагентами как необязательная аналитика; операции должны работать без договора. |
| CREATE | catalog | `cash_flow_item` | Статьи движения денежных средств. |
| CREATE | operation | `goods_receipt` | Поступление товаров от поставщика. |
| CREATE | operation | `service_receipt` | Поступление услуг от поставщика. |
| CREATE | operation | `goods_sale` | Реализация товаров покупателю. |
| CREATE | operation | `service_sale` | Реализация услуг покупателю. |
| CREATE | operation | `money_receipt` | Поступление денег на расчетный счет. |
| CREATE | operation | `money_payment` | Списание денег с расчетного счета. |
| CREATE | records | `stock_records` | Записи движений товаров по складам. |
| CREATE | records | `settlement_records` | Записи взаиморасчетов с контрагентами. |
| CREATE | records | `money_records` | Записи движения денежных средств. |

Рекомендация: в базовой версии использовать именно вид `records` для учетных движений, а не только обычные `register`, потому что документация BaSYS выделяет механизм проведения операций по регистрам записей как основной способ декомпозиции хозяйственных операций в управленческом учете.

### 2.2. Справочники первой версии

**Включить обязательно:**

- `company` — почти любой учет должен понимать, от имени какой организации ведется операция.
- `counterparty` — нужен для закупок, продаж, оплат и взаиморасчетов.
- `product` — единый справочник для товаров, услуг, работ и материалов. Разделение по типу лучше сделать признаком, а не отдельными справочниками.
- `product_group` — иерархическая или классификационная группировка номенклатуры.
- `unit` — нужен для количества в товарных и сервисных строках.
- `warehouse` — нужен для товарного учета; при отсутствии физического склада может использоваться как виртуальное место хранения.
- `bank` и `bank_account` — нужны для платежей и реквизитов.
- `cash_flow_item` — нужен для классификации поступлений и списаний денег.

**Включить, но сделать необязательным в операциях:**

- `contract` — договор почти всегда появляется в реальном бизнесе, но для самой простой модели не должен блокировать ввод операций. Поэтому договор лучше создать в ядре, но не делать обязательным полем: все операции первой версии должны работать без договора.

**Сознательно не включать в первую версию:**

- сотрудники, подразделения, проекты, кассы, валюты, ставки НДС, налоги, статьи затрат, статьи доходов и расходов, партии, серийные номера, характеристики номенклатуры, цены, прайс-листы, статусы заказов;
- эти сущности важны, но они не универсальны на уровне минимального ядра и должны появляться отдельными блоками.

### 2.3. Операции первой версии

Базовые операции должны покрывать четыре наиболее частых потока: покупка, продажа, поступление денег, списание денег.

**Товарные операции:**

- `goods_receipt` увеличивает остатки товаров на складе и задолженность перед поставщиком.
- `goods_sale` уменьшает остатки товаров на складе и увеличивает задолженность покупателя.

**Сервисные операции:**

- `service_receipt` отражает полученную услугу и задолженность перед поставщиком, но не двигает склад.
- `service_sale` отражает оказанную услугу и задолженность покупателя, но не двигает склад.

**Денежные операции:**

- `money_receipt` отражает получение денег на расчетный счет и, если указан контрагент, уменьшает задолженность покупателя или фиксирует аванс.
- `money_payment` отражает оплату денег с расчетного счета и, если указан контрагент, уменьшает задолженность перед поставщиком или фиксирует аванс выданный.

Разделение товаров и услуг на разные операции выбрано для простоты пользователя и для упрощения проведения: товарные документы двигают склад, сервисные — нет.

### 2.4. Регистры первой версии

Минимальный набор учетных регистров:

1. **Остатки товаров по складам** (`stock_records`)
   - аналитики: период, организация, склад, номенклатура;
   - ресурсы: количество, сумма;
   - используется товарными поступлениями и реализациями.

2. **Расчеты с контрагентами** (`settlement_records`)
   - аналитики: период, организация, контрагент, договор опционально, операция-основание;
   - ресурс: сумма задолженности;
   - используется покупками, продажами и оплатами.

3. **Денежные средства** (`money_records`)
   - аналитики: период, организация, расчетный счет, статья ДДС;
   - ресурс: сумма;
   - используется денежными поступлениями и списаниями.

Доходы, расходы и прибыль не входят в первую версию ядра. Для них нужен отдельный будущий блок, потому что статья движения денежных средств и статья доходов/расходов методически не одно и то же. Первая версия показывает товары, деньги и взаиморасчеты, но не рассчитывает управленческую прибыль.

### 2.5. Ключевые связи

Обязательные связи первой версии:

- операции ссылаются на `company`;
- операции закупки/продажи/оплаты ссылаются на `counterparty`;
- товарные строки операций ссылаются на `product`, `unit` и используют количество/цену/сумму;
- товарные операции ссылаются на `warehouse`;
- денежные операции ссылаются на `bank_account` и `cash_flow_item`;
- операции формируют записи в соответствующие `records`-регистры;
- `product` ссылается на `product_group` и `unit`.

Связи, которые можно отложить или сделать необязательными:

- договор в операциях;
- банк у контрагента;
- расчетный счет контрагента;
- валюта операции;
- ставка НДС;
- проект / заказ / направление деятельности;
- ответственный сотрудник;
- статья доходов и расходов как отдельный развитый справочник;
- начальные остатки товаров, денег и задолженности.

### 2.6. Ключевые алгоритмы

Алгоритмы первой версии должны быть максимально прямыми:

- при сохранении товарного поступления формируются приходные записи по складу и увеличение задолженности перед поставщиком;
- при сохранении товарной реализации формируются расходные записи по складу и увеличение задолженности покупателя;
- при сохранении поступления услуг формируется задолженность перед поставщиком без отражения управленческого расхода;
- при сохранении реализации услуг формируется задолженность покупателя без отражения управленческого дохода;
- при сохранении поступления денег увеличивается остаток денег и уменьшается задолженность покупателя / фиксируется аванс;
- при сохранении списания денег уменьшается остаток денег и уменьшается задолженность перед поставщиком / фиксируется аванс выданный.

На этом этапе не закладывать расчет себестоимости. `goods_sale` в первой версии не формирует себестоимость реализации и не показывает валовую прибыль по товарам. Расчет себестоимости, управленческих доходов/расходов и прибыли должен быть отдельным будущим блоком.

Начальные остатки товаров, денег и задолженности также не входят в первую версию ядра. Их можно будет добавить отдельным блоком начального ввода или техническими операциями после реализации базовой модели.

### 2.7. Принципы расширения модели

1. **Не дублировать ядро.** Будущие блоки должны ссылаться на `company`, `counterparty`, `product`, `warehouse`, `bank_account`, а не создавать собственные аналоги.
2. **Добавлять аналитику постепенно.** Проекты, подразделения, сотрудники, направления деятельности, партии и серийные номера должны появляться только когда задача требует такой детализации.
3. **Сохранять простую базу.** Базовые операции должны оставаться пригодными для предпринимателя без бухгалтера и методолога.
4. **Отделять управленческий учет от регламентированного.** Налоги, НДС, бухгалтерские проводки и отчетность — отдельные блоки, не часть минимального ядра.
5. **Использовать единый справочник номенклатуры.** Тип позиции определяет поведение строки: товар двигает склад, услуга склад не двигает.
6. **Расширять через новые операции и регистры, а не через перегрузку одного универсального документа.** Универсальный документ быстро становится сложным и непонятным.

### 2.8. Принципиальные компромиссы

- **Простота важнее полноты.** Первая версия должна покрывать типовые сценарии, но не обязана закрывать все методические нюансы.
- **Управленческий учет, не бухгалтерия.** Первая версия должна помогать предпринимателю видеть товары, деньги и долги, но не заменяет регламентированный бухгалтерский учет и пока не рассчитывает доходы, расходы и прибыль.
- **Операции разделены по смыслу.** Поступление товаров, поступление услуг, реализация товаров и реализация услуг — отдельные операции, чтобы не перегружать пользователя настройками внутри одного документа.
- **Договоры есть, но не обязательны.** Это сохраняет расширяемость без усложнения самого простого сценария.
- **Себестоимость не решается в ядре.** Реализация товаров в первой версии не формирует себестоимость и не показывает валовую прибыль; партионный учет, FIFO/LIFO/средняя и перепроведение задним числом требуют отдельной методики.

## 3. Рассмотренные альтернативы

### 3.1. Один универсальный документ покупки/продажи vs отдельные операции товаров и услуг

**Альтернатива:** сделать один документ покупки и один документ продажи с признаком строки «товар/услуга».

**Выбор:** разделить товарные и сервисные операции.

**Почему:** товарные документы двигают склад, сервисные — нет. Разделение делает проведение проще, формы понятнее, а будущие блоки легче проектировать.

### 3.2. Разные справочники товаров и услуг vs единая номенклатура

**Альтернатива:** создать отдельные справочники `Товары` и `Услуги`.

**Выбор:** единая `Номенклатура` с типом позиции.

**Почему:** многие бизнесы продают и товары, и услуги в связке. Единый справочник проще расширять и использовать в отчетах.

### 3.3. Не делать регистры в первой версии vs сразу заложить минимальные регистры

**Альтернатива:** сначала сделать только справочники и операции без проведения.

**Выбор:** заложить минимальные регистры записей.

**Почему:** без регистров модель не дает учета остатков, долгов и денег. Она становится набором журналов документов, а не учетной системой.

### 3.4. Полноценная бухгалтерская модель vs управленческое ядро

**Альтернатива:** сразу проектировать план счетов, НДС, налоги, проводки и регламентированную отчетность.

**Выбор:** управленческое ядро.

**Почему:** цель проекта — быстро решать прикладные задачи разных предпринимателей. Регламентированная бухгалтерия резко увеличит сложность и будет зависеть от юрисдикции, режима налогообложения и методологии.

### 3.5. Включить валюты сразу vs отложить

**Альтернатива:** сразу добавить валюты и курсы.

**Выбор:** отложить валютный учет по решению PM: первая версия работает в одной валюте.

**Почему:** мультивалютность влияет на деньги, взаиморасчеты, доходы/расходы и переоценку. Это отдельный блок.

## 4. Граница scope

- Регламентированный бухгалтерский учет и план счетов.
- Налоговый учет, НДС, УСН, ОСНО и отчетность.
- Партионный учет, FIFO/LIFO/средневзвешенная себестоимость.
- Управленческие доходы/расходы, расчет прибыли и отдельный регистр доходов/расходов.
- Начальные остатки товаров, денег и задолженности.
- Производство, сборка, комплектация.
- Розничные кассы, эквайринг, онлайн-кассы.
- CRM-воронка, лиды, сделки, задачи менеджеров.
- Зарплата и кадровый учет.
- Проекты, подразделения, центры финансовой ответственности.
- Мультивалютность и курсовые разницы.
- Интеграции с банками, маркетплейсами, 1С, Excel-импортами.
- Сложные отчеты и дашборды, кроме минимальных проверочных представлений, если они нужны для приемки.

## 5. Принятые решения PM

1. **Касса в первую версию не входит.** Учитываются только банковские расчетные счета. Касса может быть добавлена отдельным будущим блоком.

2. **Себестоимость реализации товаров в первой версии не считается.** Реализация товаров не формирует себестоимость и не показывает валовую прибыль. Себестоимость и прибыль — будущий отдельный блок.

3. **Валюты в первую версию не входят.** Первая версия работает в одной валюте без курсов, курсовых разниц и переоценки.

4. **Регистр доходов и расходов в первую версию не входит.** Первая версия не смешивает статьи ДДС со статьями доходов/расходов. Управленческие доходы, расходы и прибыль проектируются отдельным блоком.

## 6. Риски

### Риски чрезмерного упрощения

- Без регистров модель не даст реальных остатков, долгов и денег.
- Без организации будет сложно использовать модель для нескольких юрлиц или ИП.
- Без типа номенклатуры товары и услуги начнут смешиваться в логике проведения.
- Без договоров даже как необязательной аналитики позже может быть трудно расширять взаиморасчеты.
- Без статей ДДС денежный учет будет показывать только движение денег, но не смысл платежей.
- Без начальных остатков первая версия подходит для старта учета с текущей даты, но не закрывает полноценный перенос действующего бизнеса без дополнительного блока.

### Риски чрезмерного усложнения

- Если сразу добавить налоги, партии, валюты, проекты, сотрудников и себестоимость, первая версия станет слишком тяжелой.
- Универсальные документы с множеством режимов будут непонятны предпринимателю.
- Попытка сделать «почти бухгалтерию» замедлит проект и создаст методические обязательства, которые пока не подтверждены.
- Слишком много обязательных аналитик приведет к тому, что простую продажу или оплату будет трудно ввести.
