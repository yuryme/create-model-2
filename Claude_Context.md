## Где мы сейчас

Разворачиваем рабочую среду первого проекта пользователя на Claude Code. Целевая платформа — BaSYS (LowCode для бизнес-приложений). **Предметная область проекта пока не определена** — это открытый вопрос. Задача — построить решение по автоматизации через генерацию JSON-метаданных. ТЗ ещё не сформулировано.

Инфраструктура проекта **готова и проверена тестами**: рабочее пространство, документация (свой клон + индекс), референс-корпус с индексами, пустая модель в `project/metadata/`, skills-стек (cc-docs, basys-docs, basys-metadata + 6 supporting + excel-import-to-detail + два ролевых загрузчика), две ADR, шаблон ТЗ, workspace-CLAUDE.md как страховка автоподхвата контекста. Три теста подхвата контекста в свежей сессии пройдены 2026-05-16. **Подготовительный этап полностью завершён.**

**Модель работы — три роли в трёх чатах + PM:**
- **Аналитик** (`/analyst`): отдельный чат для проектирования. На крупных задачах работает в **двухэтапном цикле**: сначала короткая методика решения (`<NN>-design.md` по шаблону `_design-template.md`), после одобрения ассистентом PM — полное ТЗ. Read + Write только в `project/docs/`.
- **Инженер** (разработчик + админ, `/engineer`): отдельный чат для реализации ТЗ и поддержания инфраструктуры. Полные инструменты, может вызывать subagents для bounded-задач (research, validation, тестирование).
- **Ассистент PM** (текущий чат, без отдельной slash-команды): помощник пользователя-PM по координации между ролями, приёмке методик/ТЗ/реализаций, ведению workspace-документации (`Claude_Context.md`, `OPEN_QUESTIONS.md`, `RETROSPECTIVE.md`), оформлению ADR, retrospective. Полные инструменты, но **по своей инициативе файлы не правит** — сначала план, потом одобрение PM (правило в auto-memory `feedback_plan_before_edit.md`).
- **PM** — пользователь. Координирует роли, утверждает методики/ТЗ/реализации, удерживает архитектурное и предметное видение.
- **Все три роли ассистентов запускаются Claude Code в корне workspace** (`create-model-1/`). Пути CWD-relative от этой точки. Рекомендуемые параметры — Opus 4.7 + High thinking; PM-чат — дополнительно 1M context; Аналитик/Инженер — 1M при крупных задачах.

**Важно про референс.** `reference/metadata/` — это чужая модель (БД `elevator`, производство металлоконструкций). Используется как банк паттернов. Её **предметная область к нашему проекту отношения не имеет**, и **UID видов/типов оттуда не копировать** (см. ADR-002).

- **Эмпирика runtime `.bjs`-команд `experiment-large-01`** (2026-05-19). По ходу отладки `operation/sale.fill_cost` на стенде собран набор находок, в нескольких местах расходящихся с тем, что напрямую следует из `programmableCommands.md` и `dataTable.md`. Зафиксированы в `project/.claude/skills/basys-metadata/commands.md` (новый раздел «Эмпирические находки runtime»). Ключевое: (1) `$t.<table>` — НЕ полноценный DataTable, поддерживает только `.rows`, `.clear()`, `.load(...)` — без `toArray`/`process`/`groupBy`; (2) `QueryBuilder` к табличной части после `save()` возвращает stale-данные относительно формы — для актуального состояния читать `$t.<table>.rows` напрямую; (3) ссылочная колонка в источнике `load()` требует пары `<col>` + `<col>_display` (суффикс зависит от инсталляции — у нас `_display`, в части reference `_title`); (4) Stored-колонки с Formula НЕ пересчитываются после `load()` и `await recalculate()` — заполнять явно в источнике; (5) `alert()` в нашем runtime не показывает окно — для ошибок `throw new Error(...)`, для диагностики `console.log` + DevTools; (6) при отладке полезен версионный маркер `log('VERSION', 'vN')` в начале — без него невозможно понять, доехала ли свежая версия `.bjs` до стенда (импорт `.bjs` не всегда автоматически перезаписывает тело команды в БД, иногда требуется ручное копирование через BaSys.Constructor).
