# Проект BaSYS-AI — структура и правила

> Этот файл — инструкция по обустройству проекта для совместной работы человека и AI-ассистента (Claude Code) над метаданными BaSYS. Здесь — структура папок, соглашения, кодировки, правила использования референсного корпуса и шаблоны вспомогательных файлов Claude Code.
>
> Используется вместе с локальным клоном официальной документации BaSYS (`basys-docs/` рядом с `project/`) и его картой (`basys-docs-index.md`). Эти два артефакта — **первоисточник правды** обо всём, что касается самой платформы; данный файл — о том, как должна быть устроена работа.

> **Обновление от 2026-05-15.** Изначальная версия гайда предполагала, что базой знаний о BaSYS будет файл `basys-knowledge-base.md` (вольный пересказ другой нейросети). Он удалён за ненадобностью. Вместо него используется клон официального репозитория `BaSysTeam/BaSys.Docs` в папке `basys-docs/` плюс курируемая карта `basys-docs-index.md`. Все упоминания скилла `basys-metadata/SKILL.md` в дальнейшем тексте читать как «thin-wrapper, ссылающийся на эти первоисточники», а не как «копия knowledge-base».

## 1. Концепция

**Целевая система не редактируется напрямую.** AI генерирует и правит JSON-файлы метаданных в локальной папке. Человек глазами проверяет diff, при необходимости правит, затем вручную импортирует обновлённые папки в BaSYS через штатный механизм импорта-экспорта.

Это даёт:
- Естественный Git-флоу (версии, ветки, ревью, откаты).
- Полную безопасность — между AI и боевой системой всегда есть человек.
- Возможность работать офлайн, без доступа к экземпляру BaSYS.
- Прозрачность изменений: каждый коммит = одно осмысленное изменение метаданных.

### Два ключевых ресурса

1. **Целевой проект** (`project/`) — то, что превратится в новую систему. Изначально пустая или почти пустая модель.
2. **Референсный корпус** (`reference/`) — действующая система, экспортированная в JSON. Read-only. Источник системных UID, паттернов и готовых решений.

- Claude Code видит обе папки относительно рабочей директории и может читать `../reference/` и `../basys-docs/` явным путём.

## 3. Кодировки и переводы строк

Это болевая точка для русскоязычных проектов, поэтому правила жёсткие и фиксируются файлами-конфигами.

### Универсальное правило

Везде — **UTF-8 без BOM, перевод строки LF**.

- BOM в JSON ломает многие парсеры (Newtonsoft.Json в .NET до 2018 года имел известные проблемы с BOM, и аналогичные грабли встречаются в любом «не самом свежем» окружении).
- BOM в Git-репозиториях создаёт ложные diff'ы и конфликты, когда разные ОС редактируют один файл.
- CRLF (Windows-стиль) в JSON — допустимо, но конфликтует с тем, что Linux/macOS-инструменты выдают LF. Унификация на LF снимает класс проблем.

### `.gitattributes`

```
* text=auto eol=lf
*.json text eol=lf
*.md   text eol=lf
*.js   text eol=lf
*.yml  text eol=lf
*.yaml text eol=lf

# Бинарники
*.png binary
*.jpg binary
*.pdf binary
*.xlsx binary
```

### `.editorconfig`

```
root = true

[*]
charset = utf-8
end_of_line = lf
insert_final_newline = true
trim_trailing_whitespace = true
indent_style = space
indent_size = 2

[*.md]
trim_trailing_whitespace = false
```

### Git-настройки локального окружения

Один раз на машину:

```bash
git config --global core.autocrlf input    # на Linux/macOS
git config --global core.autocrlf false    # на Windows, если нет проблем с CRLF
git config --global i18n.commitEncoding utf-8
git config --global i18n.logOutputEncoding utf-8
```

Для Windows-консоли — убедиться, что активна UTF-8 кодовая страница (`chcp 65001`), либо использовать Windows Terminal / VS Code Terminal по умолчанию.

## 4. Именование и язык

### Что обязательно на латинице

- **Имена файлов и папок**. `sale.json`, не `реализация.json`. На разных ОС у Unicode-имён файлов разная нормализация — кириллические имена создают баги, не воспроизводимые на других машинах.
- **Поле `name`** в JSON метаданных (DataObject, MetaObjectTable, MetaObjectTableColumn). Snake_case, нижний регистр, цифры, `_`. До 30 символов. Это технический идентификатор: имя таблицы БД, ключ маршрута в URL форм, идентификатор в выражениях `$h.<name>`.
- **Имена параметров** в QueryBuilder (`@param_name`).
- **Ключи JSON-полей** — английский, по схеме BaSYS.

### Что можно по-русски

- **`title`** — отображаемое название в UI.
- **`memo`** — комментарий.
- **Содержимое полей данных** (значения в записях справочников и т.д.).
- **Строковые литералы в выражениях**, если они используются как тексты для пользователя.
- **Файлы `docs/`** — пишем по-русски как пишет команда.

### Чего не делать никогда

- ⛔ Кириллических `name` у объектов и колонок, даже если документация BaSYS их формально допускает. Это бомба замедленного действия для импорта и интеграций.
- ⛔ Пробелов и спецсимволов в `name`. Только `[a-z0-9_]`.
- ⛔ HTML-сущностей (`&quot;`, `&amp;`) и `\u` escape вместо живых символов в JSON-строках. UTF-8 пишется как есть.
- ⛔ Транслита в `title` и `memo`. Если по-русски — то по-русски.

## 5. CLAUDE.md — постоянная инструкция

Файл `project/CLAUDE.md` грузится в контекст каждой сессии Claude Code автоматически. Он должен быть **коротким** — это памятка про правила и точки входа, а не дублирование SKILL.md.

Шаблон:

```markdown
# Проект: <название>

Цель: построение системы автоматизации <предметная область> на платформе BaSYS
через генерацию JSON-метаданных, импортируемых в BaSYS вручную.

## Где что лежит

- Первоисточник о платформе BaSYS (read-only клон официальной документации): `../basys-docs/ru/`
- Карта документации BaSYS: `../basys-docs-index.md`
- Project-скилл «как мы делаем метаданные»: `.claude/skills/basys-metadata/SKILL.md` (thin-wrapper, ссылается на первоисточник выше)
- Канонические примеры JSON: `.claude/skills/basys-metadata/snippets/`
- Действующая модель как референс (read-only экспорт метаданных): `../reference/`
- Карта референсного корпуса: `../reference/INDEX.md`
- ТЗ текущей итерации: `docs/ТЗ.md`
- Лог решений: `docs/decisions.md`
- Рабочие метаданные для импорта в BaSYS: `metadata/`

## Жёсткие правила

1. Имена `name` и имена файлов — только латиница snake_case, ≤30 симв.
2. UID никогда не выдумываются. UID видов и типов берутся из `../reference/`.
   UID новых объектов оставляются пустыми/placeholder, BaSYS присвоит при импорте.
3. Все файлы — UTF-8 без BOM, LF. Без HTML-сущностей и \u-escape.
4. `title` и `memo` можно по-русски.
5. UI генерируем только при крайней необходимости — по умолчанию автоформы
   (поля listFormUid и itemFormUid оставляем пустыми).

## Рабочий поток

1. Пользователь описывает задачу.
2. Уточняющие вопросы (максимум 3 за раз, потом продолжаем работу).
3. Обновление `docs/ТЗ.md`.
4. Поиск релевантного в `../reference/` через INDEX.md.
5. Генерация/правка JSON в `metadata/`.
6. Запись принятого решения в `docs/decisions.md`.

## Чего не делать

- Не редактировать `../reference/` — это read-only.
- Не запускать импорт в BaSYS — это делает человек.
- Не предлагать программируемые компоненты UI, пока не исчерпаны
  возможности автоформ и конструктора.
```

## 6. Референсный корпус и INDEX.md

Корпус — десятки JSON-файлов рабочей системы. Целиком в контекст не грузим: расход токенов несоразмерен пользе. Вместо этого AI работает с ним по двухступенчатой схеме.

### Ступень 1: INDEX.md как карта

Файл `reference/INDEX.md` — таблица всего корпуса с однострочными аннотациями. AI читает его, чтобы знать «куда смотреть» под конкретную задачу.

Шаблон:

```markdown
# Карта референсного корпуса

Версия экспорта: <дата экспорта, версия BaSYS>
Источник: <название действующей системы>

## Catalog (справочники)

| Файл | Имя (name) | Назначение |
|---|---|---|
| catalog/contractors.json | contractors | Контрагенты. Иерархический. Реквизиты ИНН, КПП, банк. |
| catalog/nomenclature.json | nomenclature | Номенклатура. С единицами измерения. |
| catalog/warehouses.json | warehouses | Склады. Простой плоский справочник. |

## Operation (документы)

| Файл | Имя | Проводит по | Источники |
|---|---|---|---|
| operation/supply.json | supply | stock (Plus), settlements (Minus) | header, goods |
| operation/sale.json | sale | stock (Minus), settlements (Plus) | header, goods |
| operation/payment.json | payment | settlements (Minus), cash (Plus) | header |

## Register (регистры записей)

| Файл | Имя | Измерения | Ресурсы |
|---|---|---|---|
| register/stock.json | stock | warehouse, nomenclature | quantity, amount |
| register/settlements.json | settlements | partner, contract | amount |

## Menu, Workflow, Report — аналогично

...
```

Такая таблица занимает 100-500 строк в зависимости от размера корпуса. AI понимает структуру за один проход.

### Ступень 2: точечное чтение

Когда AI нужен паттерн — например, как делать `RecordsSettings` для документа, который проводит по двум регистрам — он по INDEX.md находит подходящий файл (например, `reference/metadata/operation/sale.json`) и читает только его. Это операция «cheap».

### Ступень 3: канонические сниппеты в скилле

Самые типичные паттерны однократно вытаскиваются в `.claude/skills/basys-metadata/snippets/` как короткие, очищенные, аннотированные образцы. Это «уменьшенные копии» реальных файлов:

- `catalog-simple.json` — пустой справочник с одной колонкой `title`
- `catalog-hierarchical.json` — справочник с иерархией (родитель/потомок)
- `operation-basic.json` — документ без проведения
- `operation-with-records-header.json` — документ, проводящий из шапки
- `operation-with-records-table.json` — документ, проводящий из табличной части
- `operation-with-records-source.json` — документ с RecordsSource
- `register-balance.json` — регистр остатков
- `menu-autofill.json` — меню с автозаполнением

Эти файлы Claude видит всегда через скилл — они дешёвые и часто используются.

### Чего НЕ делать с корпусом

- ⛔ Копировать UID объектов из корпуса в новые объекты целевой системы. UID **уникальны** — каждый новый объект должен получить свой при импорте.
- ⛔ Копировать целые файлы из корпуса в `metadata/` без переименования. Если из корпуса берётся паттерн, ставится свой `name`, очищаются `uid`, корректируется содержание.
- ⛔ Править файлы в `reference/`. Это read-only. Если структура устарела — пересоздаём корпус заново из новой выгрузки.

## 7. Slash-команды Claude Code

В `.claude/commands/` лежат шаблоны частых сценариев. Минимальный набор для старта:

### `.claude/commands/new-entity.md`

```markdown
---
description: Создать новый объект метаданных (справочник, документ, регистр)
---

Создай новый объект метаданных. Спроси у пользователя:
1. Тип: catalog / operation / register / report / menu / иной
2. Назначение (одной фразой)
3. Какой ближайший аналог есть в ../reference/

После ответов:
1. Открой ../reference/INDEX.md и найди аналог.
2. Прочти его файл, выпиши паттерн.
3. Сгенерируй новый файл в metadata/<kind>/<name>.json
4. Пройди чек-лист из SKILL.md раздела 14.
5. Покажи итог пользователю на ревью.
```

### `.claude/commands/add-records-rule.md`

```markdown
---
description: Добавить правило проведения по регистру в существующий документ-операцию
---

Спроси:
1. Какой документ?
2. В какой регистр пишем?
3. Направление (Plus / Minus)?
4. Источник: шапка, табличная часть или RecordsSource?

Затем:
1. Найди в ../reference/ похожее правило проведения.
2. Скопируй паттерн, замени UID и выражения под нашу задачу.
3. Добавь блок в RecordsSettings документа.
4. Проверь, что Period задан через выражение (обычно $h.date).
5. Покажи diff.
```

### `.claude/commands/find-similar.md`

```markdown
---
description: Найти в референсном корпусе объект, похожий на задачу
---

Получи от пользователя описание задачи в свободной форме.
1. Прочти ../reference/INDEX.md.
2. Подбери 1-3 наиболее похожих объекта по назначению/структуре.
3. Прочти их файлы.
4. Резюмируй: что из них можно переиспользовать как паттерн.
```

Slash-команды запускаются в Claude Code как `/new-entity`, `/add-records-rule`, `/find-similar`.

## 8. Журнал решений (`docs/decisions.md`)

Журнал в стиле ADR (Architecture Decision Record) — короткие записи про каждое значимое архитектурное решение. Шаблон записи:

```markdown
## 2026-05-15: Использовать единый регистр взаиморасчётов вместо двух

**Контекст.** Рассматривались варианты: (а) отдельные регистры для авансов и долгов, (б) единый регистр взаиморасчётов с положительными/отрицательными остатками.

**Решение.** Выбран вариант (б).

**Обоснование.** Соответствует паттерну из reference/operation/payment.json, упрощает запросы.

**Последствия.** Все документы оплат и реализаций проводят в один регистр `settlements` со знаком, отчёт по дебиторке группирует по партнёру и считает sum.
```

AI добавляет такие записи **самостоятельно**, когда принимает архитектурное решение совместно с пользователем. Это сильно облегчает работу в будущих сессиях — Claude видит контекст решений, а не угадывает заново.

## 9. Поток первого запуска

Что делает пользователь, открывая проект первый раз в Claude Code:

1. **Создаёт корневую рабочую папку** (например, `basys-workspace/`) и кладёт в неё `project-setup-guide.md`.
2. **Клонирует официальную документацию BaSYS** в `basys-docs/` рядом с гайдом: `git clone https://github.com/BaSysTeam/BaSys.Docs.git basys-docs`. Создаёт `basys-docs-index.md` снаружи клона как карту-указатель по `basys-docs/ru/`.
3. **Создаёт подпапку `reference/`** и при наличии — выкладывает экспорт BaSYS действующей модели в `reference/metadata/`. Если экспорта пока нет — оставляет каталог пустым с README-заглушкой.
4. **Создаёт подпапку `project/`** для будущего Git-репозитория.
5. **Создаёт `.claude/skills/basys-metadata/SKILL.md`** в `project/` — **тонкий wrapper**, который описывает правила работы с метаданными BaSYS и явно ссылается на `../../../basys-docs/ru/` и `../../../basys-docs-index.md` как на первоисточник (НЕ копирует содержимое документации внутрь).
6. **Создаёт `CLAUDE.md`** в корне `project/` — по шаблону из раздела 5.
7. **Создаёт `.gitattributes` и `.editorconfig`** в `project/` — по шаблонам из раздела 3.
8. **Инициализирует git** в `project/` и делает первый коммит.
9. **Запускает Claude Code** в папке `project/`.
10. **Первый промпт Claude Code:**
    > Прочти SKILL.md и пробегись по карте документации `../../basys-docs-index.md`. Затем — по карте корпуса `../../reference/INDEX.md` (если она уже создана). Если `reference/INDEX.md` ещё нет — составь его сам, обойдя `../../reference/metadata/` и сделав однострочные аннотации по схеме из `project-setup-guide.md` раздел 6. После этого подтверди, что готов начать проектирование, и предложи первый шаг.

После этого можно описывать задачу и работать.

## 10. Поток сессии — пошагово

Типовая итерация:

1. **Пользователь формулирует задачу.** Может быть в любой степени детализации: от «нужен учёт продаж» до «добавь колонку `discount` в табличную часть документа `sale`».

2. **AI задаёт уточняющие вопросы** (не более 3 за раз). Например: «Используем единый регистр взаиморасчётов или отдельные?», «Скидка процентом или суммой?», «Применяется к каждой строке или ко всему документу?»

3. **AI обновляет `docs/ТЗ.md`.** Это живой документ задачи, не финальный текст ТЗ — он растёт по мере уточнений.

4. **AI ищет в `../reference/`** через INDEX.md аналогичный паттерн.

5. **AI генерирует / правит JSON** в `metadata/`.

6. **AI показывает diff** пользователю.

7. **Пользователь ревьюит, при необходимости просит правки.**

8. **AI записывает архитектурное решение** в `docs/decisions.md`, если оно было принципиальным.

9. **Пользователь коммитит** изменения в Git.

10. **Когда набирается осмысленная партия изменений** — пользователь импортирует обновлённые папки `metadata/` в BaSYS, проверяет работу. Если что-то не так — откатывается через Git и итерирует.

## 12. Чего ждать, чего не ждать

**Чего стоит ждать.** Claude Code хорошо справится с:
- Генерацией структурно правильных JSON-файлов по чёткому ТЗ.
- Поиском и переиспользованием паттернов из референса.
- Написанием выражений `$h./$r.` и JS-источников записей.
- Базовыми SQL-запросами через QueryBuilder.
- Поддержанием консистентности именований и кодировок.

**Чего ждать не стоит на первом этапе.**
- 100% правильных UID. UID видов и типов берутся из референса; UID новых объектов BaSYS присвоит при импорте. Если в процессе обнаружится, что какой-то UID указан неверно — это нормальный итерационный момент.
- Полностью корректных регламентированных Excel-отчётов с первой попытки. Это сложная часть, требует ручной доводки.
- Понимания тонкой бизнес-логики предметной области из коротких описаний. Уточняющие вопросы — норма, а не показатель плохой работы AI.

**Когда что-то идёт не так.**
- Если AI начинает выдумывать UID — стоп, проверить, есть ли INDEX.md и читает ли AI референс.
- Если AI предлагает программируемые Vue.js-формы вместо автоформ — напомнить про правило 70% автоформ из SKILL.md.
- Если в JSON появляются HTML-сущности или \u escape — проблема в чтении/записи файла, проверить кодировки.
- Если diff содержит изменения переводов строк во всём файле — проблема в `.gitattributes` или Git-конфиге.

## 13. Что дальше

После первой успешной итерации (1-2 простых объекта в `metadata/` импортируются в BaSYS и работают) — расширять корпус сниппетов, добавлять slash-команды под повторяющиеся сценарии, накапливать паттерны в `docs/decisions.md`.

Со временем `.claude/skills/basys-metadata/` станет всё более точной моделью «как мы делаем BaSYS» — это и есть желаемое поведение: проект учится у самого себя через AI.

## Послесловие

Эта структура — не догма. Если в ходе работы выяснится, что какой-то слой лишний (например, slash-команды используются редко) или, наоборот, не хватает (нужна отдельная папка для конфигов окружений) — переустраивайте. Главное держать три инварианта:

1. **Референс read-only**, изменения только через переэкспорт.
2. **Метаданные — JSON, UTF-8 без BOM, LF, snake_case в технических именах.**
3. **AI работает с файлами, человек — с BaSYS.** Эту границу не размывать.

Удачи. Базы у вас отличные: чёткая модель метаданных, выгрузка/импорт через файлы, прозрачные правила. Дальше — дело техники и итераций.
